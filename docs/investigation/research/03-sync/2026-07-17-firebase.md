As-of: 2026-07-17

## What it is
Cloud Firestore is Google's proprietary managed document database with realtime listeners and built-in offline caching, sold via Firebase (app platform) and GCP. **No self-hosting exists or ever will** — the Emulator Suite is dev-only. GA since January 2019; actively invested (Firestore Enterprise edition with MongoDB compatibility went GA 2025-08-26). Bus factor is Google: the database itself is core GCP infrastructure and will outlive any startup on this list, but Firebase-branded satellites do get killed — Dynamic Links was shut down 2025-08-25, links went 404. Vendor death is not the risk; **vendor exit is**: proprietary wire protocol, proprietary SDKs, managed export requires the paid plan and lands in a GCS bucket in a non-portable format. Leaving Firestore later means rewriting Koi's entire sync layer.

## Client support
Best-in-landscape breadth, with one asterisk. Web: first-class TS SDK (`firebase-js-sdk`), offline persistence **opt-in** via `persistentLocalCache()` (IndexedDB, single- or multi-tab). Swift: first-class native SDK, offline on by default. React Native: the JS SDK runs but **its persistence layer is web-only — no offline cache in RN** (open FR firebase-js-sdk#7947); real offline requires `@react-native-firebase` (Invertase's wrapper around the native iOS/Android SDKs, v26+ requires RN New Architecture). Works, widely used, but Koi's flagship platform then depends on a third-party wrapper Google doesn't maintain.

## Sync model
- **Granularity:** document = record. Per-record identity comes free (S-1 superficially fits). 1 MiB/doc hard cap, so Document blobs go to Cloud Storage for Firebase — which has **no offline story at all** (uploads need network; offline blob queue is DIY). New projects have required the Blaze (pay-as-you-go) plan for Storage buckets since 2024-10-30.
- **Conflicts: last-write-wins, full stop.** No vector clocks, no CRDT, no custom merge hooks anywhere. Concurrent offline edits to the same field: the write that reaches the server last silently overwrites the other. Field-level `update()`s to *different* fields interleave safely; same-field edits lose input with no trace — a direct violation of Koi's "deterministic convergence with no silent loss" (S-3). Security rules can only accept/reject, not transform or flag; rejecting a replayed offline write strands the client's local state.
- **The offline queue is a black box.** Pending writes replay automatically on reconnect, in order, before app code can inspect, dedupe, or veto anything (even *detecting* the pending queue is an open FR, firebase-js-sdk#3661). Transactions **fail when offline** (documented), so read-modify-write guards are online-only.
- **Tombstones: none.** `delete()` erases the doc; a device returning after months replays its queued `set()` and **resurrects it**. "Erase everything must propagate durably" (S-8) is defeatable by design; a DIY tombstone collection can't help because the SDK replays the queue before your code runs.
- **Offline depth:** cache defaults to 100 MB with LRU eviction (configurable/unlimited); docs warn verbatim that "offline query performance can suffer when users are offline for long periods of time." Built for intermittent disconnection, not months-offline devices.
- **Where app logic runs:** client `onSnapshot` listeners fire on merged remote changes; Cloud Functions triggers (`onDocumentWritten`, TS, Blaze-only) run server-side post-write, at-least-once.

## Fit vs Koi criteria
1. **Privacy: fails at the floor.** Only rung reachable is **server-readable, on Google's servers, no self-host possible**. E2EE is impractical: rules, queries, and Functions all evaluate plaintext server-side; client-encrypted fields would break every query and the invariant hook. No-accounts sync is impossible — anonymous auth mints a *per-device* UID and cannot join 2–4 devices to one dataset; multi-device requires a real Google/Apple/email sign-in. Local-only-no-account mode and opt-in sync are salvageable, but "private car tracker, data readable by Google" is the bottom of Koi's #1 criterion with no ladder up.
2. **Invariant preservation: half-works, on rotten foundations.** The odometer question has a concrete yes: a client `onSnapshot` listener (or a TS Cloud Function writing to a `violations` collection) observes post-merge state and can queue monotonicity violations for review — "flag, never fix" is expressible. But LWW silently discards concurrent input *before* the checker ever sees it; the losing write is unrecoverable, so flagging operates on already-lossy state. S-3 violated underneath the feature that works.
3. **Offline depth: medium-poor.** Fine for days, documented degradation for long offline, LRU may evict cached data, RN needs the native wrapper, web persistence opt-in and session-persistent (a caveat for shared machines), blobs have zero offline support.
4. **Solo maintainability: the best on the list.** Zero infra, mature SDKs, enormous docs/community. This is the axis Firebase exists to win.
5. **Cost: trivially fine.** Free tier (1 GiB, 50k reads/20k writes/day) dwarfs Koi's scale; Blaze needed for Storage + Functions but PAYG ≈ €0–2/mo.
6. **Maturity: Google-grade longevity, maximal lock-in.** Five-year survival near-certain; the exit cost and the Dynamic Links precedent are the real liabilities.

## Cost sketch
€0–2/mo realistic (Blaze plan, usage within always-free quotas; a few GB of blobs ≈ cents). Budget alert advisable. Cost is not the problem.

## Red flags
- Server-readable-by-Google is the *only* privacy rung; self-host impossible; multi-device requires a real account. Fails Koi's #1 criterion outright.
- LWW with silent loss; no merge hooks; opaque auto-replaying offline queue that app code cannot veto (S-3).
- No tombstones — returning devices resurrect deleted docs; S-8 unenforceable.
- Docs explicitly disclaim long-offline performance; transactions fail offline.
- RN offline hinges on a third-party native wrapper; JS SDK persistence is web-only.
- Total proprietary lock-in; export path is Blaze-gated and non-portable.

## Verdict
**Refuse** — fails the top-weighted criterion (privacy) at the floor with no mitigation, and its conflict model violates locked sync requirements S-3 (silent loss) and S-8 (durable erase); unbeatable maintainability and cost cannot buy back a first-criterion fail.
