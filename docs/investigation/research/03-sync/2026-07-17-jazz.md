# Jazz (jazz.tools) — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
Jazz is Garden Computing's sync framework — but as of mid-2026 it is **two products in transition**. "Classic Jazz" (v1, `garden-co/classic-jazz`, MIT, 2.5k stars) is the CRDT-based "collaborative values" (CoValues) framework with E2EE and cryptographic permissions; it peaked at **0.20.x without ever reaching 1.0** (latest release `cojson-storage-sqlite@0.20.19`, 2026-07-03) and its README now says "we recommend using Jazz v2 for new projects." **Jazz v2** (`garden-co/jazz`, MIT, ~130 stars) is an **alpha** ("entirely new API", prerelease channel locked to `alpha`) repositioned as "a local-first relational database." The v2 announcement (blog "What is Jazz?", 2026-04-18) states the pivots explicitly: permissions moved **from cryptographic enforcement to "a trusted server applying richer policies at sync time"**, and concurrency moved from CRDT replay to "a more git-like snapshot model," with E2EE reduced to "room for encrypted fields where they matter." Company: Garden Computing, Inc. — **5 people** (founder Anselm Eickhoff + 4 engineers, gcmp.io/team, 2026-07-17); **no publicly disclosed funding** (Tracxn listed it unfunded as of 2025; PitchBook profile shows no public rounds). Monetization is Jazz Cloud.

## Client support
TypeScript-first throughout. Classic: React, React Native (dedicated RN + Expo docs), Svelte, Vue, vanilla TS, plus server-side Node "Server Workers". v2: React, Vue, Svelte, Solid, Expo/React Native (`jazz-rn` package, alpha), plain TS, Rust; "direct SQL access coming soon." No Swift-native client in either line.

## Sync model
**Classic:** sync unit = CoValue (CoMap/CoList/CoFeed/FileStream) — record-level granularity maps cleanly to Koi records. CoMaps merge **last-writer-wins per key**, but every edit from every device is retained: `$jazz.getEdits()` exposes full per-field history (value, author account, timestamp), so nothing is silently lost — losing writes remain inspectable. Clients `subscribe` to CoValues and observe merged state as remote edits land. App/server logic: Server Workers are ordinary Jazz peers with their own keypair; they have "no special or privileged access" — to read E2EE data they must be added to the group. Deletes: `deleteCoValues` marks a **tombstone** (loads as `loadingState: "deleted"`); physical erasure is async and "dependent on the sync server's configuration"; Jazz Cloud backups "may persist until overwritten." Blobs: FileStream/ImageDefinition, designed for exactly Koi's downscaled-image/PDF case. Unknown-field round-trip is structural: clients append edits per key rather than rewriting objects, so old clients don't strip new fields. **v2:** partial table sync, durable streams and files, git-like branching/merge, row-level policies in `permissions.ts` enforced server-side; auth = anonymous (read-only) / local device secret / external JWT. Merge/conflict detail is thin — it's alpha.

## Fit vs Koi criteria
1. **Privacy:** Classic genuinely hits **E2EE-with-account** — and the account is a client-side keypair with no email/PII (anonymous account auto-created; passkey/passphrase only needed to add a second device — which Koi needs, so the no-account rung is out). "Your data is always encrypted, even on Jazz Cloud servers" (classic encryption docs). Self-hostable via `npx jazz-run sync` (Node ≥20, SQLite). **But v2 — the only version the vendor recommends — is server-readable** with optional encrypted fields. The privacy rung Koi wants lives on the legacy track.
2. **Invariant merge:** good on Classic. Odometer answer, concretely: client subscribes to the per-car log; on any merged remote edit it re-sorts by date, detects monotonicity violations, and writes review-queue entries as ordinary CoValues — "flag, never fix" works because LWW never drops history (`getEdits()` recovers every conflicting input) and the engine never rejects writes. Server-side checking is possible via a Server Worker but requires group membership, i.e. surrendering E2EE to your own server. v2: unknown; branch/merge semantics not yet documented.
3. **Offline depth:** Classic is fully offline-first (local SQLite on RN, background sync); months-offline devices replay logs and receive tombstones. Solid.
4. **Solo maintainability:** framework does a lot (auth, sync, storage, files) — low bespoke infra. But you inherit framework churn: schema API rewrites were frequent even within 0.x, and now a v1→v2 migration looms. CSV-import/recurrence idempotency needs app-level dedup keys (CoValue IDs are random, not content-derived).
5. **Cost:** trivially fine. Jazz Cloud Starter **$0** (100 MAU, 10 GB storage, 2 GB blob egress/mo); Indie **$4/mo**; or self-host on a ~€5/mo VPS.
6. **Maturity:** the killer. 4 years to 0.20 without a 1.0, then a ground-up API reset to alpha; 5-person unfunded company whose flagship rewrite abandons the E2EE positioning. If the vendor dies: MIT code and self-hosted sync survive, but you own a large abandoned framework.

## Cost sketch
€0/mo (Starter tier covers 2–4 devices, low-thousands of records, a few GB of blobs) or ~€5/mo self-hosted VPS. Cost is a non-issue.

## Red flags
- Vendor recommends against the only version (Classic) that meets Koi's privacy bar; v2 is alpha and server-readable by design.
- v1 never shipped 1.0; API reset in 2026 signals another multi-year stabilization runway.
- 5-person team, no disclosed funding, revenue tied to Jazz Cloud adoption.
- Classic physical deletion is sync-server-configuration-dependent; Cloud backups retain deleted data — weakens "erase everything propagates durably."
- No content-derived IDs: import/recurrence dedup is bespoke app work.

## Verdict
**Refuse** — Classic Jazz fits Koi's criteria 1–3 remarkably well, but adopting a framework its own 5-person unfunded vendor has moved past (in favor of an alpha that drops E2EE) fails maturity so badly it overrides the fit.
