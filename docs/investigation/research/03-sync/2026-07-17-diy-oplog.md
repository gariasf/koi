# DIY op-log / event sourcing over Postgres — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
Not a product — a design-space option: Koi builds its own sync as a per-record operation log, following proven prior art. Two sub-architectures:

- **Variant A — HLC message log, dumb relay server** (Actual Budget / James Long's "CRDTs for mortals"): every local write emits messages `(dataset, row, column, value)` stamped with a hybrid logical clock. Clients apply messages to local SQLite and push them to a server that only stores and forwards them (optionally as opaque encrypted payloads). A merkle trie over base-3 HLC timestamps lets two peers find their divergence point cheaply, even after months apart. Per-field last-write-wins by HLC gives deterministic convergence. Actual Budget has run this in production since ~2019: MIT, 27.6k stars, 5,274 commits, monthly releases through v26.7.0 (2026-07-02) — a local-first personal-finance app, i.e. Koi's closest possible sibling. jlongster's reference implementation is ~639 lines of client + 132 of server.
- **Variant B — server-authoritative mutation rebase** (Replicache strategies doc; Linear's engine): clients send named mutations, the server re-runs them against canonical Postgres, clients rebase speculative state. Replicache is free/open and in maintenance mode (Rocicorp moved to Zero, Apache-2); its strategies doc remains the best writeup. Linear: IndexedDB bootstrap + websocket delta packets, transaction queue. Excellent UX prior art, but the server must read plaintext — server-readable rung only.

Variant A is the fit for Koi; B is cited for contrast. License: your own code. Bus factor: you — no vendor can die, but nobody else maintains it either.

## Client support
All-TypeScript by construction: one shared TS sync core (HLC, merkle, apply loop, invariant checks) consumed by React Native (expo-sqlite/op-sqlite) and web (wa-sqlite/OPFS or IndexedDB). Exactly Actual's loot-core layout. Nothing exists until you write it — persistence adapters per platform are part of the bill.

## Sync model
Granularity: per-field messages, satisfying S-1 (record identity/versioning) natively; derived values simply never emit messages. Tombstones = an LWW `deleted` field (Actual's approach): undo is writing `deleted=false`, survives sync; cascades emit child tombstones in one atomic batch. Unknown fields round-trip because messages are field-granular — an old client stores messages it can't interpret and re-applies after upgrade (a design point you must implement). Idempotency: messages are content-addressed by (timestamp, node); re-import/recurrence dedup rides on stable record IDs. Blobs: out of band — encrypted content-addressed objects in VPS disk or S3-class storage, referenced from records; a second small subsystem to build. Erase-everything: needs an explicit epoch/reset protocol (server holds a sync-group generation, like Actual's "reset sync"); a device returning after months with the old epoch is forced to discard its log and re-bootstrap, rather than resurrecting deleted data.

## Fit vs Koi criteria
1. **Privacy — 5/5, the only option reaching the top rung.** E2EE with the server as an encrypted-blob relay is the Actual model (AES-GCM key derived from a password; server cannot read budget data; note Actual's E2EE is one-way and unrecoverable on password loss). Self-hosted single-tenant, "account" degenerates to a pairing secret → **E2EE-no-accounts** is genuinely achievable. Local-only/no-sync is the default state, not a mode.
2. **Invariant preservation — 5/5.** You own the apply loop, so the required behavior is the natural one: after applying a pulled message batch, run the shared TS invariant package over affected cars and queue violations for review — flag, never fix, never reject. Field-level LWW merges concurrent edits to different fields losslessly; same-field conflicts keep the losing value in the retained log, so it can be surfaced. No engine to fight.
3. **Offline depth — 4/5.** Months-offline is the designed-for case (merkle diff, full log retained). Caveats are yours to handle: HLC implementations reject messages beyond a max clock drift (needs UX), and log/tombstone GC is constrained by the maximum offline window (fallback: force re-bootstrap when too far behind).
4. **Solo maintainability — 2/5, the crux.** The core is small, but Koi owns HLC, merkle trie, wire format, message-schema migration (messages live forever — versioned format + upcasting), E2EE key management, blob pipeline, epoch/reset, and convergence testing (property-based multi-device fuzzing is non-optional). Honest estimate: 150–250 h to a trustworthy v1 — 4–6 months of the entire 10 h/week budget — plus permanent sole ownership of the nastiest bug class.
5. **Cost — 5/5.** One small VPS (Hetzner CX-class, ~€4–6/mo as of 2026-07) runs Node + Postgres — or SQLite server-side, as actual-server does; blobs are a few GB. Far under €25/mo.
6. **Maturity — 3/5.** The pattern is production-proven for ~7 years by an actively shipping MIT project; your implementation starts at zero. Bus factor is literally 1, but there is no vendor-death scenario: data always lives in local SQLite plus free export.

**Odometer question, concretely:** yes — merge is your own `applyMessages()`; post-batch, recompute the per-car trail and enqueue monotonicity violations client-side. The (E2EE-blind) server never needs to see plaintext to support this.

## Cost sketch
€4–6/mo VPS + backups (~€1) ≈ **€5–8/mo**. The real cost is time, not money.

## Red flags
- 150–250 h build before Koi features resume; schedule risk against 10 h/week.
- Convergence bugs are silent and solely yours; requires disciplined fuzz/property testing.
- Message-schema migration is forever (upcasting old ops); erase-everything and tombstone GC need bespoke protocols vs months-offline devices.
- Blob sync is a second bespoke subsystem.
- No community backstop when stuck.

## Verdict
**Shortlist** — the only path to E2EE-no-accounts, a perfect "flag, never fix" hook, and ~€5/mo infra; earned despite the 2/5 solo-maintainability score, and it must beat the best off-the-shelf E2EE engine in a Phase 5 spike to survive.
