# Zero (Rocicorp) — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
General-purpose sync engine from Rocicorp (Aaron Boodman/Erik Arvidsson, ex-Chrome/Gmail; ~7 people; successor to Replicache and the now-deprecated Reflect). Architecture: `zero-client` (TS library with a local cache) + `zero-cache` (server process holding a read-only SQLite replica of your Postgres via logical replication) + your own API server hosting the mutation push endpoint. Postgres is the single source of truth; Boodman calls Zero "just a fancy cache." **Zero 1.0 shipped 2026-06-08** — first stable release after ~2 years, described as a symbolic bump from 0.26.2 with no breaking changes (InfoQ, 2026-06). Client and server are **Apache-2.0**; Rocicorp monetizes via a managed service (invite-only launch was slated Q4 2025; no public pricing found as of 2026-07-17) and paid support. Bus factor: small company, deliberately non-rocketship ("built to last" positioning), but they have deprecated two prior products (Reflect deprecated, Replicache maintenance-only); funding reports conflict (Tracxn "unfunded" vs. "$7M raised"). Apache-2 server code means self-hosters survive vendor death.

## Client support
TypeScript-first. React and **React Native/Expo officially supported** (as-of 2026-07: identical API to web, needs a `kvStore` — `expo-sqlite` or the faster `op-sqlite`; official `zslack` Expo sample). Web via IndexedDB. No Swift-native client (irrelevant under the RN hypothesis). Bundle is heavy: 718 KB uncompressed / 232 KB gzipped (InfoQ, 2026-06).

## Sync model
- **Granularity:** row-level; clients declare *synced queries* and zero-cache streams matching rows. Meets S-1 (record = row) naturally; derived values just stay out of Postgres.
- **Writes:** *mutators* — named TS functions that run optimistically on the client, then replay **server-authoritatively** at your push endpoint. `ServerTransaction.dbTransaction` exposes the raw Postgres connection, so the server mutator can run arbitrary validation/SQL in the same transaction. Client speculative state is rolled back and replaced by authoritative server results (rebase).
- **Conflicts:** effectively resolved by server serialization of mutators; no CRDT merge. Deterministic convergence because clients are caches of Postgres.
- **Deletes/tombstones:** server-authoritative row deletion; tombstones/undo are app-schema concerns (doable — soft-delete columns). "Erase everything" propagates trivially: a returning device just re-syncs current server state, and it *cannot* carry months of unsynced local writes (see below).
- **Blobs:** no attachment story; unsupported Postgres column types (incl. `bytea`, `array`) are **silently dropped from replication** (docs, postgres-support, 2026-07). Document scans would need separate app-managed object storage.
- Postgres-only; views not synced; no SSR.

## Fit vs Koi criteria
1. **Privacy:** worst rung only — **server-readable**. zero-cache holds a full replica of synced data and evaluates queries/permissions server-side, so E2EE is architecturally impossible. Self-hosting (strong plus per charter) is real and Apache-2, but the floor also cracks: "fully functional local-only with no account" fails because *writes require connectivity to the server*.
2. **Invariant preservation:** actually excellent *for online writes*. The server mutator is a perfect hook: run the shared TS invariant package (or SQL checks) post-write, insert rows into a `violations` review-queue table, never reject — "flag, never fix" falls out naturally, and clients observe the queue via a synced query. But the flagship scenario (two devices log odometer readings *offline*, merge later) **cannot occur** — because offline writes cannot occur.
3. **Offline depth: fails hard.** Reads from already-cached data work offline; **all writes are rejected** in `disconnected`/`error`/`needs-auth` states. This is an explicit design decision ("the cost to support offline is extremely high... not a priority right now" — docs/offline, accessed 2026-07-17); the roadmap even lists "disable offline writes" as a shipped feature. Koi's requirement — capture identical with no network, devices returning after months — is unmeetable.
4. **Solo maintainability:** moderate. Three server pieces (zero-cache, Postgres with `wal_level=logical` and a non-pgbouncer direct connection, your API server) vs. Koi's zero-server today. All TS, good docs, but more infra than a doc-sync engine.
5. **Cost:** fine. Single-node example is 1 vCPU/2 GB; a €5–10/mo VPS runs zero-cache + Postgres at Koi scale, plus a few €/mo object storage for blobs. Under €25/mo.
6. **Maturity:** 1.0 (June 2026), active, credible team, permissive license — but a 7-person shop with a history of sunsetting products, and community sentiment at 1.0 was "great DX, cautious on production readiness."

## Cost sketch
Self-host: Hetzner-class VPS €5–10/mo (zero-cache + Postgres single node) + ~€1–5/mo S3-compatible storage for scans ≈ **€10–15/mo**. SaaS: pricing unpublished as of 2026-07-17.

## Red flags
- Offline writes rejected by design; explicitly deprioritized — no committed timeline.
- E2EE impossible; server reads everything (mitigated only by self-hosting).
- No blob/attachment support; `bytea` columns silently dropped from sync.
- Vendor has deprecated its two previous sync products (Reflect, Replicache-in-maintenance).
- Requires Postgres with logical replication + your own push-endpoint server: three moving parts for a 2–4 device single-user app.

## Verdict
**Refuse.** Criterion 3 is disqualifying on its own: Zero is deliberately online-first and rejects offline writes, while Koi requires identical capture with no network and devices returning after months. Privacy also tops out at the lowest rung. Worth a parking-lot note: the server-authoritative mutator model is the cleanest invariant-hook design seen so far — revisit only if Rocicorp ever ships offline writes.
