# Yjs — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
CRDT **library**, not a sync platform: shared types (Y.Map/Y.Array/Y.Text) inside a Y.Doc, delta updates over any transport, provider ecosystem for network/persistence. MIT. Created and still primarily maintained by Kevin Jahns; v13.6.31 released 2026-05-28, 22.2k GitHub stars, ~900k weekly npm downloads — the most deployed CRDT in production (Jupyter, Evernote, the Tiptap/ProseMirror ecosystem). Funded via the Y-Collective open collective (Ably $85k, Cargo/Saga $12k each) plus contract work (ZenDiS/DINUM fund Yjs 14: changesets + attribution, previewed at FOSDEM 2026). Bus factor: core is effectively one person, mitigated by funding, the huge user base, and the yrs Rust port. Because it's an MIT library with self-hostable servers, vendor death does not brick the app.

## Client support
TypeScript: first-class (JS with shipped typings). Web: first-class incl. y-indexeddb persistence. **React Native: core runs (pure JS, minor Hermes polyfills) but there is no maintained persistence provider** — y-op-sqlite is 25 stars, last push 2024-06-14, no license; plan on writing a small SQLite update-log persistence layer yourself. Swift: yswift binding to yrs exists if the RN hypothesis falls through. Servers: hocuspocus 4 (v4.3.0, MIT, Tiptap-maintained, Node/Bun/Deno/CF Workers), y-sweet (MIT, Rust+S3, Jamsocket — v0.9.1 2025-09-16, last commit 2025-12-04, seven months quiet), y-websocket (reference), Liveblocks Yjs (SaaS, active, server-readable).

## Sync model
Wire unit is the doc (delta updates + state-vector catch-up); **merge granularity is per operation — per field if each record is a Y.Map keyed by record ID** in a parent Y.Map. Satisfies record-level identity (S-1). Verified empirically on v13.6.31 (local two-doc merge tests, 2026-07-17):
- Two devices adding **different** records or touching **different fields** merge losslessly.
- Concurrent writes to the **same field** = deterministic LWW by clientID. The **winning device gets no event and has no public API to see the losing value**; only the losing device sees it (event `oldValue`, `txn.origin`/`local:false` distinguish remote sync). This is silent loss in the S-digest sense.
- **Merge logic is not customizable.** App code observes merged state via `observe`/`observeDeep` with transaction origin — the post-merge hook Koi needs exists and works.
- `Y.Map.delete` wins over a concurrent edit and drops it silently (verified) → Koi must never use native delete for records; model tombstones as app-level soft-delete fields, which also yields undo-that-survives-sync. Cascades: one Yjs transaction = one update, applied atomically on peers. "Erase everything" vs a months-offline device needs an app-level epoch (rotate doc GUID, reject old epoch) — bespoke but small.
- **Unknown fields survive only under edit-in-place discipline**: rewriting a record as a fresh Y.Map destroys fields the old client didn't know (verified) — a standing foot-gun for schema evolution, enforceable in the shared TS data layer.
- Blobs: **no attachment support**; Y.Doc lives fully in memory, so multi-MB scans need a separate blob store (S3/R2, content-addressed refs in records).
- Growth: 3,000 records ≈ 650 KB encoded; +30,000 field edits → ~950 KB (measured). Deleted content GCs to tombstone markers. Trivial at Koi scale.

## Fit vs Koi criteria
1. **Privacy** — best rung: **E2EE-with-no-accounts is achievable**, because updates are opaque binary and the relay can be dumb (store-and-forward encrypted updates; devices share a key). But nothing turnkey: secsync is the only ready protocol (Apache-2.0, **self-declared beta**, 232 stars, zero releases, NLnet-funded solo project); otherwise DIY relay with client-side snapshot/compaction (server can't merge ciphertext). Server-readable rung is turnkey (self-hosted hocuspocus/y-sweet). Local-only, no account, opt-in sync: trivially yes — the library is fully functional with no provider. Self-hostable: strongly yes.
2. **Invariant preservation** — the odometer question, answered concretely: yes. Each device runs the shared TS invariant package inside an `observeDeep` handler filtered to remote-origin transactions; on merge it re-sorts the affected car's trail, detects monotonicity violations, and queues them for review. Nothing is auto-fixed or rejected — "flag, never fix" fits Yjs's never-reject merge model naturally. The deduction: fixed merge semantics mean concurrent same-field edits lose one side silently (winner can't even flag it). Koi's flagship case (two *new* readings) is unaffected; same-record concurrent edits by one user are rare but the requirement says *no* silent loss — closing that gap needs per-field versioning or edit-history modeling on top.
3. **Offline depth** — excellent. State vectors mean a device returning after months exchanges exactly the missing deltas; no server-side log expiry (doc state is the store). Best-in-class here.
4. **Solo maintainability** — the weak point. Koi must build: RN persistence, blob side-channel, app-level tombstones + epoch erase, E2EE protocol (or adopt beta secsync), and edit-in-place discipline. Each is small; together they're a sync product's worth of glue for 10 h/week.
5. **Cost** — self-host hocuspocus or y-sweet on a Hetzner CX22 (~€5/mo) + R2 for blobs (€0–1 at a few GB). Well under €25. No license fees.
6. **Maturity** — core 5/5 and vendor-death-proof; the Koi-relevant periphery is thin: y-sweet slowing, secsync beta, y-op-sqlite dead. Ecosystem gravity is rich-text collab, not record ledgers — Yjs 14's headline features are editor-oriented.

## Cost sketch
€5–6/mo total: one small VPS (relay + Postgres/SQLite for update storage) + object storage for blobs. Zero if piggybacking on an existing box. SaaS (Liveblocks/Tiptap Cloud/Jamsocket) unnecessary and server-readable.

## Red flags
- Silent LWW loss on concurrent same-field writes, unobservable on the winning device (verified) — direct S-digest violation absent data-model workarounds.
- Whole-record replace strips unknown fields; native map delete drops concurrent edits (both verified) — correctness rests on team discipline encoded in the data layer.
- No blob story; whole doc in memory.
- RN persistence ecosystem effectively nonexistent.
- E2EE path is beta or DIY.
- Single-maintainer core (funded, but still).

## Verdict
**Possible** — superb, cheap, vendor-death-proof core with the exact post-merge hook Koi needs, but Koi-shaped usage requires five pieces of bespoke assembly plus a workaround for silent same-field LWW loss; a strong fallback if record-native engines disappoint, not the default pick.
