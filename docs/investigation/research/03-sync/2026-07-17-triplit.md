# Triplit — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
Full-stack TypeScript syncing database: an embedded client DB (pluggable storage: memory, IndexedDB, SQLite/expo-sqlite) syncing over WebSockets to a Node/Bun/Cloudflare-Worker server with SQLite/LMDB durable storage. Built by Aspen Cloud (YC W21, founded 2020, team of 3, founders Matthew Linkous and Will Ernst). License: **AGPL-3.0-only for the entire monorepo, including all client packages** (verified on npm, 2026-07-17).

**The project is effectively dead.** As of 2026-07-17: every `@triplit/*` npm package was last published **2025-07-31** (npm registry timestamps); last commit to `main` was **2025-09-11**; the only repo activity since is two AI-generated experiment branches (Postgres adapter 2025-12-30, TPC-C benchmark 2026-01-19), never merged. **triplit.dev returns HTTP 410 Gone** — homepage, docs, blog, everything (checked directly 2026-07-17); search snippets show the domain listed for sale. **Y Combinator's company profile lists Triplit as "Inactive"** (checked 2026-07-17). Triplit Cloud (the managed SaaS) had already closed to new users before the site vanished (deprecation callout in in-repo docs, Sept 2025 snapshot). No shutdown announcement was ever posted; the GitHub repo (3.1k stars, ~40 open issues) is not archived but has no maintainer response since late 2025. Bus factor was 2; both have walked away.

## Client support
First-class TypeScript everywhere. Web (IndexedDB storage), React/Vue/Svelte/Solid/Angular bindings, TanStack integration. React Native supported on Hermes via `@triplit/react-native` + `ExpoSQLiteKVStore` (expo-sqlite adapter). No Swift-native client. Local-only mode: omit `serverUrl`/`token` and the client runs fully offline with durable local storage, sync can be added later — architecturally a good match for Koi's "local-first, sync opt-in" floor.

## Sync model
- **Granularity:** per-entity, decomposed to per-attribute. Each attribute is a Last-Writer-Wins register with Lamport timestamps (their own FAQ's words). Concurrent writes to different attributes of one record merge cleanly; concurrent writes to the *same* attribute: highest timestamp wins, **loser is dropped silently** — the engine surfaces nothing (violates Koi S-req "losing input is surfaced or merged losslessly"; detectable only indirectly because the winning value flows back through subscriptions).
- **Offline:** true offline-first. Optimistic local writes, durable outbox (IndexedDB/SQLite), auto-reconnect, delta-based partial replication per subscribed query; docs claim convergence "even those that have been offline for an extended period."
- **Custom merge logic:** none. No pluggable merge, no server-side hooks/triggers/webhooks (docs and server config expose none). Server is a black-box Docker image (`aspencloud/triplit-server`) configured via env vars; schema permissions are the only server-side logic surface.
- **Observing merged state (odometer question):** yes, client-side. Live query subscriptions fire on every incoming remote delta, and `onSyncMessageReceived` exposes raw sync messages. Koi could subscribe to each car's fuel-log query and re-run the monotonicity check after every subscription callback, queueing violations for review — "flag, never fix" is implementable entirely in app code, and LWW never rejects a write, so nothing is dropped at the record level. This works; it just has no engine support and no server-side backstop.
- **Deletes:** `client.delete()` exists; tombstone semantics, resurrection behavior vs long-offline writers, and durable "erase everything" propagation are **undocumented**. Unverifiable now that docs are offline and maintainers gone.
- **Blobs:** no file/attachment support at all. Koi's document scans would need a fully separate bespoke blob channel.
- **Unknown fields:** schema-checked on server (`onEntitySyncError` fires on schema-check failure); old-client round-trip of new fields unverified — likely a migration hazard.

## Fit vs Koi criteria
1. **Privacy:** best rung achievable is **server-readable, self-hosted**. No E2EE at any cost (server executes queries over plaintext). Floor is met: local-only mode, no account, self-host, opt-in sync. Rung 3 of 3.
2. **Invariant merge:** post-merge client-side flagging works via subscriptions (score-worthy), but attribute-level LWW silently discards concurrent same-field input, tombstones undocumented, no server hook. Partial fit.
3. **Offline depth:** genuinely strong — the best part of the product. Months-offline edge cases now permanently unpatchable.
4. **Solo maintainability:** adopting Triplit in 2026 means becoming the sole maintainer of an abandoned ~24-package AGPL monorepo with a dead docs site. Unacceptable for 10 h/week.
5. **Cost:** free software; self-host on a €5–10/mo VPS with SQLite. SaaS no longer exists. Within budget — irrelevant given the above.
6. **Maturity:** company Inactive (YC), website 410, zero releases in ~12 months, no successor steward. Five-year survival: effectively zero.

**AGPL-3.0-only on the client** is a further blocker: shipping Koi's iOS/Android apps linked against AGPL libraries obliges releasing the full app source under AGPL.

## Cost sketch
Self-host only: single Docker container + SQLite on a Hetzner/Contabo VPS, ~€5–9/mo. Blob storage separate (+€1–5/mo object storage) and entirely DIY.

## Red flags
- Vendor dead: YC "Inactive", triplit.dev HTTP 410 (domain reportedly for sale), Triplit Cloud closed, no announcement, no handover (2026-07-17).
- No releases since 2025-07-31; last main commit 2025-09-11.
- AGPL-3.0-only client packages — copyleft reaches the shipped apps.
- No blob/attachment support; tombstone/erase semantics undocumented; same-attribute LWW loses input silently.
- Documentation only exists inside the repo now.

## Verdict
**Refuse** — the technical shape (TS-native, RN + web, real offline-first, local-only mode) was one of the closest fits in the landscape, but the company is dead, the code is unmaintained AGPL, and Koi would be built on an orphan.
