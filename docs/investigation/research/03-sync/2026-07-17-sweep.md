# Landscape sweep (engines off the canonical list) — Phase 3 sync landscape brief
As-of: 2026-07-17

Completeness sweep over Evolu, RxDB, TinyBase, cr-sqlite, WatermelonDB, SQLSync/Graft, Ditto, Turso, Convex, DXOS, Verdant, Fireproof, Loro. Three earn mini-briefs; the rest get one-line dismissals. Nothing fundamentally new beyond these surfaced in mid-2026 sweeps (FOSDEM 2026 local-first track, awesome-local-first list, checked 2026-07-17).

## Mini-brief 1: Evolu — the only native rung-1 candidate

**What/status:** TS library + local-first platform on SQLite, MIT. `@evolu/common` latest 7.4.1 (2025-11-29); `8.0.0-next.5` published 2026-05-07 — active, but mid-major-version churn after a full rewrite (Effect dependency removed, new binary sync protocol). Primary author Daniel Steigerwald; small contributor base, ~1.9k stars — bus factor ≈1. No VC treadmill: monetization is apps/support, not hosting.
**Clients:** React, React Native, Expo, Svelte, vanilla JS — TS-first with typed schemas. No Swift SDK. Web via wasm SQLite.
**Sync model:** mutation log of CRDT messages `(table, row, column, value, HLC timestamp)` — column-level LWW, per-record identity ✓ (S-1). Deletes are soft (`isDeleted` system column, data never physically deleted) — tombstones + undo survive sync ✓. Relay is E2EE-blind: sees only OwnerId, timestamps, encrypted PADMÉ-padded blobs; stateless, Docker/self-hostable, runs on serverless; `free.evoluhq.com` for testing only. No blob/attachment story — Koi document scans need a separate encrypted-blob channel (e.g. S3 + keys in records).
**Odometer post-merge:** merge happens client-side in SQLite; reactive queries (`useQuery`/subscribe) re-fire on any applied remote change, so a client invariant checker can recompute per-car monotonicity after sync and queue violations — "flag, never fix" fits naturally. No server hooks exist and can't (relay can't read data): all invariant logic is client-side, which matches Koi's requirement. Caveat: same-field concurrent writes resolve by LWW silently — the losing column value isn't surfaced (tension with S-digest "losing input is surfaced"); rare in single-user multi-device but real.
**Cost:** €0 software + ~€5–10/mo VPS or free-tier Workers. Verdict: **shortlist**.

## Mini-brief 2: RxDB — mature and excellent on paper, premium wall kills it

**What/status:** v17.4.0 (2026-07-13), Apache-2.0 core, very active; one-founder company (pubkey/Daniel Meyer) funded by premium plugins. Backend-agnostic "git-like" replication protocol (pull/push/conflict endpoints); document-level sync = per-record identity ✓; client-side custom `conflictHandler` ✓; `_deleted` tombstones ✓; attachments plugin exists; observable change streams make post-merge invariant checks straightforward (client-side, or server-side since you own the backend).
**The wall:** production SQLite storage (the only serious RN persistence) and WebCrypto encryption are premium — from $99/mo billed annually (~€1,100/yr), no solo tier. The free SQLite "trial" storage is capped at 500 non-deleted docs, no indexes — Koi's low-thousands of records exceed it. E2EE is DIY on top of field encryption (server-readable rung by default).
**Verdict: refuse on criterion 5** — the architecture fits Koi well (record-level, tombstones, custom merge, RN+web TS), but the required premium tier is ~4× the entire infra budget, permanently.

## Mini-brief 3: TinyBase — cheap and reactive, but rung 3 only

**What/status:** v9.2.0 (2026-07-11), MIT, extremely active; effectively one maintainer (James Pearce) — bus factor ≈1. Reactive tabular store with `MergeableStore` CRDT: cell-level LWW via hybrid logical clocks + hashes. Synchronizer over WebSocket/BroadcastChannel; self-host `ws-server` with pluggable persister (Cloudflare Durable Objects option). Expo SQLite persister gives RN persistence; web via IndexedDB/OPFS. Listeners fire on remote merges (reactive UI on sync is the demoed pattern), so post-merge odometer checks work client-side.
**Gaps for Koi:** no E2EE and none planned — self-hosted server stores readable mergeable content (rung 3, self-host softens it); cells are strings/numbers/booleans only — no blob story, and Koi's relational model (34 invariants, typed records) maps awkwardly onto its loose tabular schema; deletes propagate via CRDT metadata but app-level undoable tombstones are still DIY.
**Verdict: possible** — best-in-class DX/cost for a toy, but loses to Evolu on privacy (criterion 1) with no compensating advantage.

## One-line dismissals (all checked 2026-07-17)

- **cr-sqlite (vlcn):** npm 0.16.3 published ~2 years ago; effectively dormant (author now at Rocicorp on Zero) — refuse.
- **WatermelonDB:** alive (0.28.0, Apr 2025) but sync is fully BYO-backend — it's the DIY-oplog brief plus native-module maintenance, no privacy edge — refuse.
- **SQLSync:** superseded by author's Graft (Mar 2025, Rust storage engine, early/experimental, no TS app framework yet) — refuse both; watch Graft.
- **Ditto:** enterprise mesh-sync SaaS (POS/aviation), opaque enterprise pricing, server-readable cloud — refuse.
- **Turso offline sync:** public beta since Mar 2025, engine mid-rewrite (libSQL→Turso), server-readable cloud, no E2EE — refuse for now.
- **Convex:** server-authoritative reactive SaaS; offline is optimistic-update depth, not months-offline capture; server-readable — refuse.
- **DXOS/ECHO:** ambitious P2P platform (ECHO+HALO identity), niche adoption, heavy runtime, RN support unclear — refuse.
- **Verdant:** one-person IndexedDB web framework, no React Native — refuse.
- **Fireproof:** encrypted git-like ledger DB, TS-everywhere, interesting crypto — but doc-oriented, beta-grade querying, weak RN story, startup bus factor — refuse (nearest miss).
- **Loro:** polished CRDT library (1.0, 2024) — same DIY-everything shape as Automerge, already covered by peer brief — refuse.

## Red flags (Evolu, the survivor)

- Bus factor ≈1; repeated rewrites (v7 rewrite 2025, v8-next churn through May 2026) — API/protocol stability risk for a 10 h/week solo dev.
- No attachment/blob support: Koi documents need a parallel encrypted blob channel (bespoke infra, criterion 4 tax).
- Same-field LWW loses the older concurrent write silently.
- Hosted free relay is testing-only; production = self-host (fine, but mandatory).

## Verdict

**Shortlist Evolu** — the only engine in the entire landscape that natively delivers privacy rung 1 (E2EE, no accounts, mnemonic-derived identity, blind self-hostable relay) with record-level TS-native sync and client-observable merges for "flag, never fix"; its costs are bus factor and version churn, both mitigated by MIT + local-first (app keeps working if the project dies). TinyBase possible; RxDB refused on cost; all other swept engines refused.

## Evolu verification (adversarial, 2026-07-17)

Adversarial re-check of the Evolu mini-brief: every claim tested against npm registry, GitHub API, a fresh clone of `evoluhq/evolu@main` (commit 51f6ddc, 2026-07-16), the v7.4.1 tag source, and live evolu.dev docs. Method: try to refute, not confirm.

### Per-claim results

- **Versions/dates — CONFIRMED.** npm registry: `@evolu/common` dist-tags `latest: 7.4.1` (2025-11-29), `next: 8.0.0-next.5` (2026-05-07). Exactly as briefed. https://registry.npmjs.org/@evolu/common
- **MIT license — CONFIRMED.** GitHub API `license: MIT`; `LICENSE` file in repo root ("The MIT License (MIT), Copyright (c) 2023 Evolu"). https://github.com/evoluhq/evolu/blob/main/LICENSE
- **~1.9k stars, bus factor ≈1 — CONFIRMED.** 1,866 stars, 72 forks. 26 contributors total; steida (Daniel Steigerwald) has 2,605 commits, next human contributor 109 — >90% of human commits from one person. All 15 most recent commits (through 2026-07-16) are his alone. https://api.github.com/repos/evoluhq/evolu/contributors
- **E2EE-blind relay (OwnerId + timestamps + encrypted padded blobs) — CONFIRMED.** Privacy docs quote verbatim: relay sees "OwnerId… Timestamps… Encrypted binary blobs: the actual data, completely encrypted and padded to obscure size" — plus **IP addresses** (docs are explicit; brief omitted this; Tor suggested as mitigation). PADMÉ padding confirmed both in docs ("message padding (PADMÉ)") and in source (`packages/common/src/Crypto.ts`, `Protocol.ts`). https://www.evolu.dev/docs/privacy
- **Mnemonic-derived owner, no accounts — CONFIRMED** (v7 stable). Source: `Owner.ts` uses `bip39.entropyToMnemonic` (`@scure/bip39` dep) → OwnerSecret → SLIP-21 derivation of OwnerId/EncryptionKey/WriteKey. No accounts, emails, or passwords anywhere in docs or code. Pairing flow reality: second device = user manually enters the BIP39 mnemonic into `evolu.restoreAppOwner(mnemonic)`, which resets the local DB and re-syncs from the relay — implemented in v7.4.1 (`local-first/Evolu.ts:880`), documented at https://www.evolu.dev/docs/local-first. No built-in QR/device-pairing UX; mnemonic transcription is the whole story. **Caveat: on `main` (v8-next), `restoreAppOwner`/`resetAppOwner` are commented out — not yet reimplemented.** The "no accounts" claim survives; the v8-next line currently lacks the restore entry point.
- **Column-level LWW CRDT, HLC, per-record identity — CONFIRMED.** `Db.ts` (v7.4.1 and main): history stored "per table, row, and column for conflict-free merging using last-write-win CRDT"; `evolu_history(table, id, column, value, timestamp)`; `Timestamp.ts` implements hybrid logical clocks. Protocol is binary (varint/delta/RLE encoding, Range-Based Set Reconciliation) per https://www.evolu.dev/docs/api-reference/common/local-first/Protocol
- **Soft deletes — CONFIRMED.** Docs: "To delete a row, set `isDeleted`… Evolu uses soft deletes instead of permanent deletion." Physical deletion is in fact an *open feature request* (relay-side owner purge, issue #656), confirming data is never physically deleted today.
- **Reactive queries fire on remote merge — CONFIRMED at source level.** v7.4.1 `Db.ts:447`: sync `onReceive: () => postMessage({ type: "refreshQueries" })` re-runs all subscribed queries; same mechanism on main (`Shared.ts:682` posts `RefreshQueries` when `didWriteMessages`). Client-side post-merge invariant checks work as briefed.
- **React Native/Expo support is real, not vaporware — CONFIRMED with caveats.** `@evolu/react-native` 14.3.0 (2025-11-28) is a maintained package with peer deps `expo >=54`, `expo-sqlite >=16`, `@op-engineering/op-sqlite >=12`; `examples/react-expo` app in repo. Caveats: (1) v8-next bumps floors hard (expo >=55, RN >=0.83, react >=19); (2) open issue #678 "Error with expo web" (2026-06-16) plus four other June-2026 bug reports (#676, #679, #680, #681) sat ~1 month with ≤1 comment and no fix — real but rough edges, and support burden lands on one person.
- **Relay self-host via Docker — CONFIRMED; "runs on serverless" — CORRECTED.** Official image `docker.io/evoluhq/relay` with Dockerfile/docker-compose in `apps/relay`. But the relay README states "Relay standardizes on Node.js for runtime and deployment" and lists serverless (Deno, Bun, workers) under "Custom implementation: re-implement for other runtimes." Docs' "stateless, can run in any serverless cloud" is aspirational protocol design, not a shipped deployment path — and "stateless" is misleading shorthand: the Docker deployment mounts a persistent SQLite data volume storing the encrypted message log. **The "free-tier Workers" cost option in the mini-brief does not exist out of the box; budget the VPS.**
- **free.evoluhq.com testing-only — CONFIRMED.** Relay docs verbatim: "We provide a free free.evoluhq.com relay for testing, but no hosting because it's not Evolu's mission to compete with established clouds." https://www.evolu.dev/docs/relay
- **No blob/attachment story — CONFIRMED with nuance.** No attachment/file feature exists in code, docs, or the issue tracker (searched "blob OR attachment OR file": zero feature hits). Nuance: `SqliteValue` accepts `Uint8Array`, and protocol messages cap at 100 MB (`Protocol.ts: maxProtocolMessageMaxSize = 100_000_000`), so small binaries *can* live in encrypted columns — but every byte lands permanently in the append-only `evolu_history` on every device and counts against relay quota (quota errors halt the offending device's sync, `ProtocolQuotaError`). Document scans as columns would be reckless; the separate-encrypted-blob-channel plan stands.
- **~€5–10/mo VPS — UNVERIFIABLE (plausible).** No official sizing guidance anywhere. Relay is a single Node.js container + SQLite volume, so any bottom-tier VPS should carry a single-family workload; treat the number as an estimate, not a verified fact.
- **Monetization "apps/support, not hosting" — PARTIALLY CONFIRMED.** "No hosting" is verbatim in relay docs; what the actual revenue model is remains unverifiable from primary sources.

### Release cadence, issue health, protocol stability (established fresh)

- **Cadence:** stable releases were a Nov-2025 burst (7.0.0 on 2025-11-19 → 7.4.1 on 2025-11-29), then **no stable release for 7.5 months**. v8 prereleases 2026-04-03 → 2026-05-07 (next.0–next.5), then release silence — but `main` has near-daily commits through 2026-07-16 and an open "Version Packages (next)" PR (#683, 2026-07-13), so next.6 is queued. Pattern: long quiet rewrites punctuated by release bursts.
- **Issue health:** 18 open issues / 2 open PRs (GitHub search API, 2026-07-17). Backlog is mostly self-filed feature EEPs; the worry is the five user-filed June-2026 bugs answered slowly or not at all (see above) while the author refactors v8 internals. Maintenance attention is single-threaded — consistent with bus factor 1.
- **v7→v8 stability — better and worse than briefed.** Better: the **wire protocol is unchanged** — `protocolVersion` is `1` in both v7.4.1 and main, with per-owner version negotiation built into the header ("allowing Evolu Protocol to evolve safely over time"), so v8 is *not* a new sync protocol; the binary protocol shipped with the v7 rewrite (which also dropped Effect — v5 peer-depended on `effect`/`@effect/schema`, v7.4.1 has zero Effect deps, only kysely + noble/scure crypto; both confirmed via npm). Worse: v8-next churn is deep library-API breakage (DI/Run/Task API rewritten, Array module renames, test-time APIs changed across six prereleases) and **feature regressions still open on main** (`restoreAppOwner` commented out, `deleteDatabase` "not implemented" per #676). No v7→v8 migration guide exists; docs' `/docs/migrations` covers app schema evolution only. Adopting today means committing to v7.4.1 and budgeting a real port when v8 lands.
- **Docs rot:** two of the mini-brief's four evolu.dev source URLs now 404 (`/docs/how-evolu-works`, `/docs/quickstart`); current equivalents are `/docs/local-first` and `/docs/api-reference/common/local-first/Protocol`. Claims those pages backed were re-verified against the live pages and source code above.

### Verdict on the mini-brief

**Reliable — shortlist stands.** Every load-bearing claim (E2EE-blind relay, BIP39/SLIP-21 no-accounts identity, column-level LWW with HLC, soft deletes, reactive queries on remote merge, real RN/Expo packages, MIT + Docker self-host, no blob story) survived contact with primary sources. Two corrections of substance: (1) serverless/Workers relay hosting is not a shipped option — self-host budget must assume a Node VPS; (2) the v8-next line is currently missing the mnemonic-restore entry point, sharpening the existing "don't ride the rewrite" red flag rather than adding a new one. One softening: the sync protocol itself (v1, negotiated) is more stable than the "new binary sync protocol per major version" framing implied.
