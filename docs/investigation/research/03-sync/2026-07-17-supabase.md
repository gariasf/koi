# Supabase (as sync backend) — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
Postgres BaaS: managed Postgres + PostgREST (auto CRUD API), GoTrue auth, Realtime (websocket change feeds/broadcast), object Storage, Edge Functions. Core is **Apache-2.0**, self-hostable. Not a sync engine — a hosted backend you could build sync *on*. Maturity is exceptional for this landscape: **Series F 2026-06-04, $500M at $10.5B post-money led by GIC**, total raised >$1B, ~4M developers claimed, 600% YoY database growth; Series E ($100M at $5B) was only eight months earlier (2025-10). Bus factor is the best of any candidate; the Apache core plus plain Postgres underneath means vendor death leaves you a `pg_dump` and runnable OSS.

## Client support
First-class TypeScript (`supabase-js`) — web, React Native, Node — plus an official Swift SDK. But these are *online* client libraries: no local persistence, no write queue, no offline cache. Everything below the network line is yours.

## Sync model
There is none, and that's the headline finding: **as of 2026-07, Supabase still has no first-class offline/sync story**. The "using Supabase offline" discussion (github.com/orgs/supabase/discussions/357) has been open since 2020; the 2026 changelogs (through May 2026) ship agent tooling, Multigres, a Stripe sync engine — nothing offline-first. Supabase's own blog answers offline questions by pointing at partners: PowerSync (official partner page), WatermelonDB, Legend-State v3 (`syncedSupabase` plugin, created/updated/deleted-column diffing), RxDB's Supabase replication plugin. Nothing changed since our working assumption — pairing is still the only path.

Used raw as a sync backend you get: row-level CRUD via PostgREST, Realtime `postgres_changes`/broadcast for change notification (RLS-checked per subscriber; Supabase now steers heavy use toward "broadcast from database"), Postgres triggers and Edge Functions for server-side hooks, and Storage for blobs (good fit for Koi's document scans, signed URLs, RLS-scoped buckets). You do NOT get: client persistence, oplog/versioning, tombstone semantics, idempotent replay, or any merge machinery. Building Koi's S-1…S-14 on raw Supabase = the DIY-oplog brief with Supabase as the substrate — same bespoke engine, same risks, plus a BaaS dependency.

**Odometer question:** Postgres is a single serialization point, so "merge" happens only in whatever DIY offline-replay layer you build. Given that layer, the flag-never-fix hook has good homes: a Postgres trigger or Edge Function re-validates the car's odometer trail after each replayed batch and writes rows to a `violations` table, which syncs down via Realtime; clients can equally re-check after pulling. So yes, arbitrary app code can observe post-merge state (triggers/functions/Realtime) — but the merge itself doesn't exist until you write it.

## Fit vs Koi criteria
1. **Privacy:** default rung is **server-readable** (self-hosting mitigates who the server is). E2EE tooling is absent: Vault is server-side secret storage, and pgsodium transparent column encryption is deprecated ("not recommended, being removed"). Client-side encryption of record payloads + anonymous sign-ins (JWT without email) could reach roughly **E2EE-with-(pseudonymous)-account**, but it's 100% DIY key management, and opaque ciphertext columns neuter PostgREST filtering, RLS-on-content and Realtime payloads — you'd be paying for a BaaS and using it as a dumb encrypted mailbox. E2EE-no-accounts unreachable (RLS needs identity). Floor items (opt-in sync, local-only app, no trackers, export) are client-side and unaffected.
2. **Invariant preservation:** hooks are genuinely good (triggers, Edge Functions in TS/Deno, Realtime observation) — but they hang off a merge layer Supabase doesn't provide. Score belongs to the DIY engine, not Supabase.
3. **Offline depth:** zero native. supabase-js assumes connectivity. Months-offline devices, background sync, identical offline capture — all delegated to a pairing (PowerSync et al.) or hand-rolled.
4. **Solo maintainability:** managed cloud is genuinely low-ops for the backend half; but as a *sync engine* it demands the entire client engine bespoke. Self-host is heavy: ~13-service docker-compose behind Kong, 4GB RAM minimum / 8GB realistic, no managed backups/PITR/branching, single-project, upgrades manual — a real ops tax at 10h/week.
5. **Cost:** Free tier ($0: 500MB DB, 1GB storage, 5GB egress) technically fits the record volume but **pauses after 1 week of inactivity** (manual dashboard resume — unacceptable for a product), has no backups, and 1GB storage is tight for years of scans. Realistic floor is **Pro at $25/mo (~€23)** — consumes essentially the whole €25 budget by itself. Self-host: €8–15/mo Hetzner VPS + the ops burden above.
6. **Maturity:** 5/5, best in the landscape. $10.5B valuation, >$1B raised, enormous community, Apache-2.0 escape hatch.

## Cost sketch
Cloud Pro: ~€23/mo (whole budget). Cloud Free: €0 but pause-risk + no backups — fine for a spike, not for the product. Self-host: €8–15/mo VPS (8GB recommended), you own backups/upgrades. If paired with PowerSync Cloud: PowerSync free tier (2GB synced/mo) + Supabase Pro ≈ €23/mo; PowerSync Pro would blow the budget ($49/mo).

## Red flags
- Six years of "offline?" discussion with no first-class answer; offline is permanently a partner story, and Supabase's roadmap energy (agents, Multigres, Stripe sync) points elsewhere.
- Free tier inactivity pause makes the only budget-fitting cloud tier unfit for production.
- Self-host bundle is a second-class citizen (no backups/branching, 13 services, manual upgrades).
- Client-encrypting columns to climb the privacy ladder destroys the query/RLS/Realtime value you'd be paying for.

## Verdict
**Refuse as a standalone sync engine** — it isn't one, and building Koi's merge/offline layer on raw Supabase is the DIY-oplog option wearing a $25/mo BaaS. Remains a *possible hosting substrate* if a pairing engine (PowerSync) wins its own brief, but it earns no shortlist spot on its own.
