# Paper design: Koi on PowerSync (self-hosted) + TS backend — Phase 3
As-of: 2026-07-17. Capability claims re-verified today against live docs (custom-auth JWT rules, sync-rules syntax, compaction, built-in attachments, local-only usage); the engine brief's verification section (same date) covers PATCH semantics, 2xx-flag guidance, FSL, pricing.

## Topology

Devices: iPhone + (conditional) Android as RN/Expo capture peers (`@powersync/react-native` GA), web companion (`@powersync/web` GA, OPFS, multi-tab). The Swift SDK is also GA — unlike Evolu, this design does not hard-commit Phase 4 to RN. Server: one VPS, four containers — Postgres 16 (canonical), `journeyapps/powersync-service` (download path only: tails logical replication, serves buckets), `koi-api` (bespoke TS — the entire write path), Caddy. Bucket storage on Postgres (Beta; fallback = a MongoDB container; spike 4).

The server reads everything: **rung 3, server-readable, softened by self-hosting** — single-tenant, your Postgres, no analytics, no third-party processors. The privacy page cannot say "we cannot read it." It can truthfully say: *"Sync is off by default; Koi is fully functional without it. With sync on, your data is stored readably in the sync server's database — a server you (or someone you trust) run. No account, no email; devices pair by QR. No analytics, no third parties, no user content in logs. Export and full erase any time."* The E2EE-envelope variant (official pattern, blog 2025-10-08; raw tables stable in JS SDKs) is deliberately **not** mainline: it forfeits server-side validation — this design's reason to exist — while still requiring JWT auth, plus ~30–60 h of key-vault and mirror-table plumbing. A footnote only.

Auth with a no-accounts feel: `koi-api` prints a one-time pairing QR; the device trades the scanned secret for a long-lived random **device token** (Keychain/IndexedDB). PowerSync JWTs must expire ≤24 h (verified today), so the token is exchanged at `koi-api` for short-lived Ed25519-signed JWTs verified against the API's static JWKS; `sub` = owner id, plus a `device_id` claim. Revoking a device = deleting one row. No email, no password, no IdP.

## Record model

One Postgres table per entity — `car`, `odometer_reading`, `fuel_log`, `log_entry`, `plan`, `plan_swap`, `trip`, `insurance_policy`, `document` (metadata only), `reminder`, `income`, `violation`, `settings`; non-synced: `device`, `pairing`. Shared columns: `id` uuid (client-generated UUIDv7 — S-1), `owner_id` (S-14), timestamps, `deleted_at` (tombstone), `row_version` bigint (trigger-bumped — S-2: server-assigned, no distributed clock; UI equality = id+row_version, so remote edits invalidate exactly like local ones), `base_version` (client-echoed, see S-5), and `extra jsonb` for unknown fields. Money in integer minor units.

S-3: no derived columns anywhere — no `current_odometer` on `car` (delta inv. 11), no economy, no cap state; `@koi/domain` computes them from watch-query results; the server computes them transiently for validation, never stores. Plan lineage is **not** a `carIDs` array column (whole-column LWW silently drops a concurrent swap — the Evolu review's A1 lesson): `plan_swap` append-only child rows union-merge losslessly; order is derived; concurrent appends are flagged.

S-10: UPDATEs upload as PATCH — row id + changed columns only (verified) — so a stale client's edit cannot strip columns it doesn't know; new fields ship as nullable columns, invisible to old clients but intact. Import-era oddities live in `extra`, selected by sync rules so every client round-trips it.

Sync rules — one per-user bucket family (S-14-ready):

```yaml
bucket_definitions:
  owner:
    parameters: SELECT request.user_id() as uid
    data:
      - SELECT * FROM car WHERE owner_id = bucket.uid
      # …one line per synced table, violation and settings included
```

## The odometer walkthrough (flagship)

**Jul 10, device A, offline.** User logs 50,200 km. `@koi/domain` entry validation (inv. 9, hard) passes against A's local trail; KoiStore writes to local SQLite; the SDK queues the insert. Saved moment instant, zero network (S-11).

**Jul 12, device B, offline.** Logs 50,150 km. B's trail lacks A's reading; passes locally; queued.

**A comes online.** `uploadData()` POSTs the CRUD batch to `koi-api`. One Postgres transaction: insert row, run `@koi/domain`'s trail check over the car's canonical trail — monotone, no flag. Replication → service → buckets → devices.

**B comes online.** Its reading uploads. The API **inserts it — 2xx always, never a rejection** (the documented pattern; a 4xx would wedge B's whole upload queue). The post-write check now sees Jul 10 → 50,200 vs Jul 12 → 50,150: inv. 9 violated in stored data. Same transaction: upsert into `violation` — deterministic id = hash(car_id + offending reading ids), kind `odometer_monotonicity`, refs to both records, status `open`. Flag atomic with data; nothing dropped, nothing repaired (S-4/S-5).

**Merge point:** Postgres, transactionally, in arrival order — no CRDT. **Observation point:** each client applies the downloaded checkpoint atomically; watch queries re-fire; both readings and the violation row land together. The review queue is literally `SELECT * FROM violation WHERE status='open'` — a synced row, so A, B, and web show the identical Home card ("2 odometer readings disagree — Review"). The detail names both records, opens either; the user edits or tombstone-deletes one (undoable), or keeps both. On later trail writes the API re-derives; a violation whose id no longer derives is marked resolved — flag hygiene, never data repair. The entry-time hard stop stays purely local, unchanged.

## Where the ~100 invariant tests run

`@koi/domain`: pure TS, zero PowerSync imports — validation, trail/economy/money math, violation derivation, Tier-1 tests, torture fixtures. Three surfaces, one package, one version (monorepo): **(a) client on write** — KoiStore validates before the local write; **(b) server on every upload** — the same functions against canonical Postgres inside the write transaction; **(c) client post-merge** — optional watch-query re-derivation as offline belt-and-braces. Bypass-proofing is structural: `koi-api` is the *only* writer — devices hold no DB credentials, the service's role is replication/read-only, the API's role holds the sole write grant. This server backstop is what no client-only shortlist design has: even a buggy future client cannot land unvalidated data unflagged. Same-field concurrency (S-5): clients echo `base_version`; if it trails `row_version` on the same column, the API applies the write (never rejects) and preserves the overwritten value in a `concurrent_edit` violation — deterministic, server-side, no log forensics.

## The rest of S-coverage

- **S-6:** delete = PATCH `deleted_at`; undo = clear it, any device (the toast holds an id). Car cascade = parent tombstone only; derivations exclude children of tombstoned cars, so peers never observe a half-deleted car (single-row atomicity). A record uploaded offline for a car tombstoned elsewhere: accepted, flagged `orphaned_child` — not dropped, not resurrected. Inv. 30's *purge* is real: after typed confirmation the API physically `DELETE`s the subtree; REMOVEs replicate; local rows drop — something append-only engines can't offer (modulo backup retention, a sign-off item).
- **S-7 — the easy one, shown:** `/erase` in one transaction TRUNCATEs all owner tables, deletes blob files, revokes every device token and pairing secret. Online devices receive REMOVEs and empty out. A months-late device is **fenced by auth**: its JWT exchange fails, so it can neither re-upload its queue nor resync — the app explains, offers local export or wipe. No marker protocols, no races. Residual: Postgres backups until rotation (~30 days), stated on the privacy page.
- **S-8/S-9:** next occurrence id = UUIDv5(reminder_id, anchor, n) — both devices materialize the same id; the API upserts `ON CONFLICT DO NOTHING`. Import: `imported_vehicle_id` unique index; record-level natural key (vehicle + date + amount + odometer + **source-file ordinal**, so legitimate money-only twins survive — Evolu review A3 lesson) as a unique hash index; the same CSV from two offline devices converges; same-key groups soft-flagged.
- **S-11:** local SQLite is the app's database; sync is background catch-up; capture identical offline, online, dead-server. A dead VPS pauses sync, never capture.
- **S-12:** synced prefs = `settings` singleton row; device-local prefs stay in platform storage. **S-13:** each device schedules locally from synced state; web never notifies.
- **S-14/D-007:** buckets are already parameterized per user; household = a `member` table + parameter-query join + a second pairing flow; permissions live in `koi-api`; `owner_id`/`device_id` exist from day one, so nothing hard-codes a single actor. The easiest sharing extension on the shortlist.

## Blobs

Built-in attachments helpers (RN ≥1.30, Web ≥1.33, Node, Swift, Kotlin — verified today; the standalone `@powersync/attachments` package is deprecated in their favor). Queue states, retries, and integrity checks come free; the attachment-state table stays local-only; the synced metadata is the `document` row. The remote-storage adapter targets **`koi-api` `/blobs/:id` on the same VPS disk** — no S3, no third-party processor, per the delta's server rules; files bypass the PowerSync service entirely. A few hundred multi-MB scans ≈ a few GB on an included 40–80 GB volume: ~€0. Not client-encrypted at rung 3 (the server reads the rows anyway); the E2EE variant would start here.

## Migration

Fresh install: local-only mode is first-class — the SDK runs without `connect()` using **local-only tables** (documented pattern), so no upload queue accrues. Bootstrap: install → import legacy JSON offline via `@koi/importer`: legacy ids map through UUIDv5(legacy-namespace, legacyId) so re-import and two-device import converge; rows insert in dependency order through KoiStore; suspect sequences flagged locally (imports never hard-fail). Enabling sync: scan pairing QR → device token → move local-only tables into synced tables in one transaction (documented flow — spike 3) → uploads queue → `koi-api` applies with `ON CONFLICT` dedup and re-runs the invariant pass; flags land in `violation` everywhere. Second device/restore: pair → initial sync pulls the full bucket (low thousands of rows ≈ a few MB) + lazy blob downloads.

## Ops & cost

Hetzner CX22-class VPS (2 vCPU/4 GB), compose stack as above. **€8–13/mo** (VPS €5–9, snapshots + offsite encrypted `pg_dump` €1–3, domain ~€1); blobs €0. Backup: nightly `pg_dump` + blob dir, encrypted offsite; restore is `psql < dump` — boring, provable. The honest solo cost is **operational**: Postgres majors, service upgrades, sync-rules deploys, JWT key hygiene, a weekly `compact` cron (self-hosted Docker command — verified), and the classic footgun: **a stopped service container leaves a logical-replication slot retaining WAL until the disk fills** — needs an alert. Budget ~½ day/month steady-state, more in year one. Months-offline device: checkpoint reconciliation; worst case after compaction CLEARs is a full bucket re-download — at Koi's scale a few MB, bandwidth not data loss. Vendor death: **strongest exit in the field** — data is ordinary Postgres you already run; client SDKs Apache/MIT; each FSL service release auto-converts to Apache-2.0 after 2 years; the write path never depended on the vendor. Worst case you replace the download path and keep the API, schema, domain package, and every byte.

## Risks & spike candidates

Pre-registered kill criteria:
1. **One-VPS reality** — full stack on 4 GB; 5k-record initial sync on mid-range Android over mobile data. Kill: OOM/instability, or initial sync in minutes-plural.
2. **Write-path round trip** — two simulators, offline conflicting odometers → upload → violation atomicity → checkpoint down. Kill: flag not atomic with data as observed, or API errors wedge the upload queue.
3. **Local-only → sync-on migration** — real dataset through the documented table-move. Kill: data loss or forced wipe.
4. **Postgres bucket storage (Beta)** — restarts, compaction, slot recovery. Kill: corruption, or a forced MongoDB fallback that breaks the 4 GB budget.
5. **S-5 base_version protocol** — concurrent same-field edits yield exactly one `concurrent_edit` flag carrying the losing value. Kill: PATCH granularity can't distinguish disjoint-field merges from same-field overwrites.

## Honest weaknesses

- **Rung 3 on a rung-1-weighted criterion.** Privacy is the #1 criterion and this is the floor rung, dressed well. "We cannot read it" is unavailable; the design bets that self-hosted single-tenant + zero third parties is acceptable — an owner's call, not an engineering fact.
- **The E2EE upgrade path cannibalizes the design**: envelopes delete the server validation that justifies PowerSync over a blind relay — rung-2 costs for rung-3-minus benefits.
- **The write path is a second product**: pairing, token exchange, upload endpoint, cascade, erase, blobs, base_version protocol — ~120–180 h ≈ 12–18 weeks at 10 h/wk before torture tests, though the invariant core is needed on any candidate.
- **Real infrastructure to keep alive**: replication slots, Beta bucket storage, four containers; a blind relay is a dumber, calmer server. If the VPS dies, sync (not capture) is down until you fix it — you are the on-call.
- **Fair-source server** (FSL, Apache-2.0 after 2 years per release) is a philosophical wrinkle for a privacy-first product, even if practically irrelevant.

## Adversarial review (2026-07-17)

Method: S-1…S-14 walked against the design's mechanics; suspicious engine-capability claims re-verified against primary sources (docs.powersync.com, powersync.com blog, PowerSync release notes) beyond the brief's existing verification section. Verdict: **sound-with-fixes** — no fatal hole; five majors that must amend the design before it competes at the gate, none of which changes the rung or breaks the cost envelope.

**Engine claims verified (all hold, two with teeth):** TRUNCATE is replicated and handled — PowerSync removes the truncated table's rows from its replica (docs note care needed truncating FK-connected groups: truncate the whole group), so the `/erase` REMOVE propagation is mechanically real · JWT ≤24 h max (86,400 s iat→exp), 60 min recommended — **and a JWT cannot be revoked once issued short of rotating the signing key** (docs.powersync.com/configuration/auth/custom), which feeds A2 below · local-only → synced table move is the documented pattern and the moved rows do enter the upload queue (docs: Local-Only Usage) — the migration section stands · write checkpoints: "while changes are present in the upload queue, the client does not advance to a new checkpoint" and backend writes must be synchronous (docs: client architecture / write checkpoints) — this both *confirms* the walkthrough's ordering (a device uploads before it observes the merged state) and *sharpens* the wedge risk (a 500ing upload blocks that device's downloads too, not just uploads) · PATCH-changed-columns-only, 2xx-flag guidance, built-in attachments, FSL/pricing already primary-sourced in the engine brief's verification section.

### Major findings

**A1 · S-5: the base_version protocol as specified can't deliver its promise — and it self-flags.** Two mechanical gaps. (a) *Attribution:* `row_version` is one bigint per row; "if it trails `row_version` on the same column" requires knowing *which columns* changed between the client's base and current — metadata the schema doesn't carry. Without per-column versioning the API must either flag every stale-base write (disjoint-field concurrent edits — A edits `station`, B edits `liters` — produce false `concurrent_edit` flags) or under-flag (silent same-field loss, the S-5 breach). (b) *Self-flagging:* a device editing the same field twice while offline echoes the same base_version on both ops (the local `row_version` never advances offline — it is server-assigned); op 1 bumps the row to v+1, op 2 arrives with the stale base → flagged as a concurrent edit *against its own earlier edit*. Editing a note twice offline is the most ordinary sequence imaginable; as written it spams the review queue — and review-queue credibility is this design's crown jewel. Fix inside the architecture, cheap because koi-api is the sole writer: maintain per-row `col_versions jsonb` (column → last row_version that touched it) + last-writer `device_id` per column; flag only when the overwritten column's last writer is a *different* device and the base trails that column's version. Spike 5's kill criterion anticipated (a) but not (b); the design text ("deterministic, server-side, no log forensics") must be amended to name this metadata, not imply row_version suffices.

**A2 · S-7: "no marker protocols, no races" overclaims — one second server-side copy and one revocation race.** (a) *Bucket storage is a second copy:* the sync service's op history retains the erased rows' full plaintext data until compaction rewrites it (that is exactly why post-compaction clients need a full re-download). With the weekly `compact` cron, an `/erase` leaves user content readable in `powersync_*` storage for up to a week — and TRUNCATE on the source tables does not touch it. Fix: run `compact` (all buckets) synchronously as part of `/erase`, and add bucket storage to the residual list alongside Postgres backups (which should also name VPS snapshots and retained WAL). (b) *Revocation race:* verified — an issued JWT cannot be revoked. A device that went offline *after* obtaining a JWT and returns within the token's lifetime (≤24 h) passes signature checks: it can re-upload its queue (partial resurrection of user content into an erased database) and stream buckets (pre-erase ops still present until compaction — plaintext disclosure post-erase). The design's fence ("JWT exchange fails") only covers devices whose JWT already expired — true for months-late devices, false inside the window. Fix, also cheap: koi-api authorizes every upload against the live `device` table (it owns the table and the box), and `/erase` rotates the JWKS keypair, killing all outstanding JWTs for the download path too. With both fixes S-7 genuinely holds; without them the claim is a race away from false. Note also: `TRUNCATE all owner tables` is only correct while the server is single-tenant — the moment a second owner exists (household, or developer-hosted users), erase must become owner-scoped DELETEs (which replicate row-level REMOVEs anyway).

**A3 · S-9: two-device CSV import convergence hand-waves the id remap — as written it either wedges the queue or mints permanent orphans.** MyCar records carry no source ids (only vehicles do); two devices importing the same CSV offline generate *different* UUIDv7s for the same rows. Device 2's upload then contains: INSERT car (dropped by the `imported_vehicle_id` unique index, ON CONFLICT DO NOTHING) + hundreds of child INSERTs whose `car_id` references a uuid the server never stored. With FK constraints: error → 500 → the upload queue wedges *and* (verified above) the device stops applying checkpoints — frozen out of sync entirely. Without FKs: the children land as synced orphans pointing at a nonexistent car, spraying `orphaned_child` flags across every device for an entire import. Neither is the promised "converges to one car set." Fix the design already half-owns: extend the migration section's deterministic-id trick to CSV import — car id = UUIDv5(owner, imported_vehicle_id); record id = UUIDv5(owner, source-vehicle-id + natural key + source-file ordinal). Both devices then mint *identical* rows; ON CONFLICT dedup becomes exact, FKs match, and the checkpoint reverts nothing. Corollary: the natural-key hash must key on the *source* vehicle id, never the local car uuid (else no two-device dedup at all), and the upload endpoint must be idempotent (upserts) under batch replay generally — a crashed batch is retried whole.

**A4 · Privacy rung: the softening argument is host-dependent, and the design never says who hosts.** "Single-tenant, your Postgres, a server you (or someone you trust) run" is true for exactly one user: the owner. The charter's declared motive includes growth (Android + web users), and the design's own S-14 story (member table, parameterized buckets) is multi-tenant-ready — but for any user who is not the operator, rung 3 means *developer-readable*, the softening evaporates, and the drafted privacy sentence would be misleading. Either the product story is per-user self-hosting (unrealistic for MyCar refugees — say so and accept the audience limit) or developer-hosted multi-tenant (then the page must say "the developer can read synced data," the weakest honest sentence on the shortlist). Separately, the drafted "No account, no email" survives only as wordplay: a persistent server-side owner identity plus revocable per-device credentials *is* an account in every sense but the email field, and the locked H1 truth table already marks that sentence ❌-rewrite at rung 3. Suggest "no email, no password; devices are authorized by QR pairing." Privacy is the #1 criterion; this design's rung-3 apology must be priced against the hosting story it actually intends, not the most flattering one.

**A5 · S-8: the duplicate exists — catch-up materialization straddling an anchor date defeats UUIDv5 collapse.** `UUIDv5(reminder_id, anchor, n)` leaves n undefined, and inv. 32's catch-up rule ("never scheduled into the past") makes the materialized occurrence a function of *today*: device A resolves a lapsed yearly (anchor Jan 5) on Dec 30 → materializes n=4, due Jan 5 '27; device B resolves the same occurrence offline on Jan 10 → Jan 5 '27 is now past → materializes n=5, due Jan 5 '28. Different ids, ON CONFLICT collapses nothing, the user gets two open occurrences (one born overdue). Fix: key identity to the *resolved parent occurrence* — next id = UUIDv5(resolved_occurrence_id) — which both devices share by construction; divergent computed dueDates on the same id are then benign first-arrival LWW (same user's intent, per the delta), and catch-up display becomes a render-time derivation (S-3 style). Also define n (occurrence ordinal from anchor + rule, counting tombstoned occurrences) for the id's provenance, never local row counts.

### Minor findings

- **S-2 as stated fails for local offline edits:** `row_version` is server-assigned, so a local edit doesn't bump it until round-trip — "UI equality = id+row_version" misses exactly the edits `revision` existed to catch. Fix: value-based diffing, or the client optimistically bumps `row_version` locally and lets the server's trigger value win at checkpoint.
- **Concurrent-upload flag race:** two devices uploading conflicting readings *simultaneously* — each transaction's post-write derivation (READ COMMITTED) may miss the other's uncommitted insert; both commit, neither flags, and no later trail write may ever re-derive. Fix: `pg_advisory_xact_lock(hash(car_id))` in the write transaction — one line, serializes per car, irrelevant at this scale.
- **koi-api totality is load-bearing, not politeness:** any 500 (poison op, FK violation, crash mid-batch) wedges that device's uploads *and* downloads (verified). The design must state: catch-all error handling (accept + flag, never throw), idempotent batch replay everywhere (not just recurrence), and an alert on stuck queues/last-seen-device age.
- **"Keeps both" is undefined downstream** (same gap the Evolu review flagged): a kept non-monotonic pair feeds distance interpolation (inv. 21–23) → negative intervals. Domain must define it — e.g. the enclosing interval yields no number, mirroring `missedPrevious` — or the code will invent or fix, both banned.
- **Purged-parent late uploads unhandled:** inv. 30 purge physically DELETEs the subtree; a device offline through the purge later uploads edits/children referencing rows that no longer exist. The API must distinguish *purged* from *never-existed* (a small purge ledger of subtree root ids) and flag without resurrecting — an upsert would silently undo a typed-confirmation purge.
- **`settings` singleton needs a deterministic id** (e.g. the owner id): two devices creating first-run settings offline otherwise mint two rows that never merge.
- **Web token eviction and pairing bootstrap unstated:** Safari ITP can evict IndexedDB (the device token) after 7 idle days → silent unpair; the re-pair flow needs a phone to mint the QR. And "koi-api prints a one-time pairing QR" — the first device's bootstrap surface (before any device is paired) needs naming: setup CLI or first-run web admin.
- **Ops undercount, time not money:** the doc itself says the WAL footgun "needs an alert" but the four-container stack includes no alerting (add healthchecks.io/uptime-kuma-class monitoring — ~€0, not ~0 h); Postgres major upgrades drop logical replication slots pre-17 → service re-replication + bucket rebuild is a runbook item; ~½ day/month is plausible only after the alerting exists. €8–13/mo money holds; the CX32 fallback (MongoDB bucket storage) also stays inside €25.
- **"Strongest exit in the field" overreaches by one word:** the DIY op-log design has no vendor at all. Strongest exit *among engines* is fair — and vendor death still strands you maintaining a frozen FSL service + Apache client SDKs against OS/SQLite churn.

### Verdict

**Sound-with-fixes.** No fatal: the flagship odometer walkthrough is mechanically real (sole-writer API, atomic flag-with-data, checkpoint atomicity, review queue as a synced row — all verified or verifiable), S-10/S-11 hold, TRUNCATE/local-only/JWT claims all survived primary-source checks, and the cost envelope survives even the fallback paths. But A1 (S-5 metadata + self-flagging) and A2 (erase's second copy + revocation race) amend locked-requirement mechanisms the current text presents as settled; A3 closes an import-convergence path that would visibly break; A4 forces the rung-3 apology to name its hosting story — the design's weakest front on the #1 criterion; A5 is the S-8 duplicate the mechanism claimed to collapse. All fixes stay inside the architecture; none changes the rung, none threatens €25/mo. Spikes 2, 4, and 5 should be re-scoped to test the *fixed* mechanisms (per-column attribution, erase-with-compact + revoked-device replay, deterministic import ids).
