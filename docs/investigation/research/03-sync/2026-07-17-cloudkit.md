# CloudKit — Phase 3 sync landscape brief
As-of: 2026-07-17

## What it is
Apple's proprietary BaaS: containers with public/private/shared databases, record zones, per-record sync, push subscriptions, CKAsset blobs. Client-side sync got first-class in iOS 17 with CKSyncEngine (WWDC23); nothing new for cross-platform surfaced at WWDC24/25 (checked 2026-07-17). Closed source, Apple-hosted only — **no self-hosting, ever**. Maturity/bus factor: Apple will outlive any alternative vendor, but the non-Swift surface (CloudKit JS, web services) has been effectively frozen for years; Apple's priorities are the risk, not survival.

## Client support
- **Swift/native**: excellent (CKSyncEngine, NSPersistentCloudKitContainer). Irrelevant to the TS-clients hypothesis.
- **Web**: CloudKit JS v2 exists and is not deprecated (docs live as of 2026-07-17), but it is stagnant — pre-Promises API, CDN-only distribution, hostile to bundlers, confusing docs (dev write-up, 2024-09-13). CRUD + queries work against private DB after Apple ID web sign-in (API token + web-auth token; expiry 30 min default, 2 weeks with "keep me signed in"). No browser push; polling or long-poll hacks.
- **React Native**: nothing official. Community bridges (react-native-cloudkit, wraps CloudKit JS) and Android's DroidNubeKit (17 commits, ~153 stars, dormant since ~2015) are dead ends.
- **Android**: no SDK, none announced. Only path is the REST web-services API — which requires **every Android user to sign in with an Apple ID in a webview**, with 2-week max token life. Non-starter for a real Android product.

## Sync model
Sync unit = record (CKRecord) in a zone; per-record change tags; atomic multi-record saves within a zone. Conflicts: save policies (`ifServerRecordUnchanged` etc.); on conflict the client receives `serverRecordChanged` with client/server/common-ancestor copies — a genuinely good primitive for lossless client-side merge. **No server-side code execution of any kind** (no hooks, functions, or triggers) — all merge and invariant logic must live in every client. Deletes propagate via zone-change feeds (server-managed tombstones); a device returning after months hits `changeTokenExpired` and does a full refetch, so erasure converges. CKAsset handles Koi's document blobs natively (always encrypted). Unknown-field round-trip is decent: CKRecord is schemaless on the client and saves field-level deltas from fetched instances.

**Odometer question, concretely**: feasible client-side. After a zone-change fetch delivers merged state, app code can re-sort the per-car trail and queue violations for review — flag-never-fix works because CloudKit hands you both sides of a conflict and never silently drops. But: the ~34-invariant checker must ship inside the Swift client, the CloudKit JS web client, and whatever the Android hack is — three runtimes unless everything is TS, which CloudKit's grain (Swift) fights. No server-side placement is possible. Web/Android clients get no push, so detection there is deferred to next app-open/poll.

## Fit vs Koi criteria
1. **Privacy** — the interesting 2026 nuance: CloudKit web services *can* read/write `encryptedValues` fields ("the web services handle the encryption and decryption for you", Apple docs) — but only because under standard protection **Apple holds the keys** (vendor-readable rung). True E2EE requires the user to enable Advanced Data Protection — per-user, opt-in, not mandatable by the developer — and ADP **disables iCloud web key access**; the re-enable grant covers only Apple's allow-listed iCloud.com services, not third-party CloudKit JS apps. So E2EE and the web companion are mutually exclusive per user. ADP was also withdrawn for new UK users under the Investigatory Powers Act (2025-02-24); the UK reportedly dropped its demand (Aug 2025), restoration not confirmed. E2EE-no-accounts: impossible (Apple ID mandatory). Self-host: impossible. Floor mostly OK (opt-in sync, local-only works, no trackers, client-side export).
2. **Invariant merge** — good conflict primitives, client-only placement, N-runtime duplication of the invariant package. Moderate.
3. **Offline depth** — excellent on Apple native (months-offline handled via token expiry + refetch); weak on web (short-lived auth tokens, no background sync).
4. **Solo maintainability** — for Apple-only Swift, near zero infra. For the actual target (RN + web + Android) it means maintaining bridges over a frozen JS SDK and a webview Apple ID flow on Android — worse than running a small server.
5. **Cost** — $99/yr developer program (~€8/mo), no server. Private DB is free to the developer but counts against **each user's iCloud quota**; free-tier users with full iCloud get sync failures the developer cannot fix.
6. **Maturity** — Apple survives; CloudKit JS is abandonware-in-place; terms can change unilaterally; data is exportable but the sync layer is unreplaceable.

## Cost sketch
€8–9/mo equivalent (developer program only). Cheapest option surveyed — and irrelevant given the platform verdict.

## Red flags
- No Android path a real product can ship (Apple ID + dormant libs + token expiry).
- E2EE (ADP) breaks the web client for exactly the privacy-conscious users; developer can't control the rung.
- ADP itself is politically fragile (UK withdrawal, Feb 2025).
- CloudKit JS frozen; no server-side logic; no self-host; total vendor lock-in.
- Contradicts the locked TS-clients working hypothesis; only fits an Apple-only Swift future.

## Verdict
**Refuse** — for a multiplatform Koi. No credible Android story, a stale web SDK whose access to encrypted data dies the moment a user opts into real E2EE, no self-hosting, and a privacy rung the developer cannot guarantee. (If Phase 4 ever reverts to Apple-only Swift, CKSyncEngine would re-enter as a serious contender — that is the one scenario where this refusal flips.)
