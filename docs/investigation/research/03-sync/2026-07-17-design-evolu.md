# Paper design: Koi on Evolu (E2EE blind-relay local-first) — Phase 3
As-of: 2026-07-17. Pinned: `@evolu/common` 7.4.1 + `@evolu/react-native` 14.3.0; API claims verified today against the 7.4.1 tag source and live evolu.dev docs. Revised same day per the adversarial review below; revision note at end.

## Topology

Devices: iPhone + (conditional) Android as RN/Expo capture peers; web via wasm SQLite. **No Swift SDK — Phase 4 is hard-committed to React Native on iOS.** Server: one VPS — the official relay Docker image (Node + persistent SQLite volume) behind a thin wrapper adding an **owner denylist** (for durable erase), plus a bespoke blob endpoint. The relay is E2EE-blind: OwnerId, HLC timestamps, PADMÉ-padded ciphertext, client IPs — nothing else (privacy docs, 2026-07-17); all merge logic is client-side.

No accounts: the first device generates a BIP39 mnemonic (→ SLIP-21 OwnerId/EncryptionKey/WriteKey); a second device runs `evolu.restoreAppOwner(mnemonic)`, wrapped in a Koi QR flow — the mnemonic is never typed or transmitted. Web keys are evictable (Safari, 7 idle days; installed PWAs exempt): QR re-pair is routine, never the sole key copy.

**Rung 1 (E2EE-no-accounts), three caveats:** the relay sees IPs; recovery is a flat mnemonic — the E2EE brief's mandated KEK→DEK indirection is forfeited (rotation = full re-key; mnemonic + all devices lost = data gone), an **owner sign-off item**, export remaining the guaranteed backup; and "zero network calls until sync is on" needs spike proof. The privacy page's rung-1 column then holds verbatim: no account/email/sign-in; "encrypted on our server — we cannot read it"; "contacts only Koi's relay, only when sync is on"; erase per S-7.

## Record model

One table per entity: `car`, `odometerReading`, `fuelLog`, `logEntry`, `plan`, `planSwap`, `trip`, `insurancePolicy`, `document` (metadata only), `reminder`, `income`, `reviewResolution`, `settings` — branded Types, money in integer minor units. S-1: ids globally unique; deterministic ids via `createIdFromString` (SHA-256, documented for cross-client convergence; 2026-07-17). S-2: per-column HLC timestamps replace `revision`; remote edits re-fire queries like local ones. Sync unit = column message `(table, id, column, value, timestamp)`.

Two S-5 mechanisms:
- **Lineage is not a column.** `Plan.carIDs` becomes append-only `planSwap` rows (planId, carId, swappedAt): concurrent swaps union losslessly, order derives from swappedAt, double-appends are flagged. Nothing to lose to LWW.
- **Edit-stamps.** Every mutation also writes `rev` = fresh id and `baseRev` = the rev edited. `evolu_history` keeps overwritten values + timestamps, app-queryable ("Evolu does not delete data — it only marks it as deleted"; time-travel doc, 2026-07-17): edits sharing a `baseRev` are provably concurrent, derived identically on every device, including one rebuilt via `restoreAppOwner`. Overlapping-column pairs surface both values for review; concurrency is never guessed from timestamps.

S-3: no derived columns — economy, current odometer, cap state, synthesized reminders, review queue are computed by `@koi/domain`. S-10: solved structurally: unknown table/column messages land in `evolu_message_quarantine` — preserved, applied on app update, propagated to peers; partial messages split. Additive-only evolution is Evolu doctrine and matches the optional-with-default law.

## The odometer walkthrough (flagship)

**Jul 10, device A, offline.** User logs 50,200 km; validation passes against A's local trail (inv. 9). `evolu.insert("odometerReading", …)` hits A's SQLite — saved instantly, zero network (S-11).

**Jul 12, device B, offline.** User logs 50,150 km. B's trail lacks A's reading; validation passes. Saved.

**Both come online.** Each syncs with the relay (WebSocket, RBSR, protocol v1), which forwards ciphertext it cannot read. B decrypts A's messages and applies them in one SQLite transaction. Distinct rows — no CRDT conflict; both readings sit in both replicas verbatim. Nothing rejected, nothing dropped (S-5).

**Observation.** After applying remote messages the worker posts `refreshQueries`; subscribed queries re-run (verified). Koi's invariant watcher — plain `subscribeQuery` per car trail — re-derives the merged trail: Jul 10 → 50,200, Jul 12 → 50,150 → inv. 9 violated in stored data.

**Flag, never fix.** The review queue is derived, never synced: violation id = stable hash(carId + offending reading ids), derived identically on A and B. Both show the Home attention card ("2 odometer readings disagree — Review", the import pattern), naming both records. Resolution: edit/delete one reading (a synced mutation; delete = undoable tombstone), or "Keep both" → `upsert` a `reviewResolution` row under the violation id — it syncs, the queue empties everywhere, concurrent dismissals collapse. A kept non-monotonic pair behaves like `missedPrevious`: the enclosing interval yields **no number**, for economy and distance alike. No auto-repair (S-4).

## Where the ~100 invariant tests run

`@koi/domain` is pure TS, zero Evolu imports: validation, trail/economy/money math, review-queue derivation, the Tier-1 tests. It runs client-side only: **(a) on write** — every mutation passes domain validation inside `KoiStore` before touching Evolu; **(b) post-merge** — the watcher after every `refreshQueries`. **Never on the server** — the relay can't read data; client-only invariants are a structural fact, not a convention. Bypass-proofing: the Evolu instance is private to `KoiStore`, which wraps mutations *and* reactive reads (lint-enforced boundary — also the exit seam); the only write-key holder is the user. CI runs it platform-free plus a two-client merge harness for the torture suite.

## The rest of S-coverage

- **S-6.** Native soft deletes (`isDeleted`); undo = clear the flag by id from any device (the toast holds an id, not a closure). Cascade = **parent tombstone only**: one message, atomic under any arrival order; derivations exclude children of tombstoned cars, so no peer renders a half-deleted car. A record arriving for a tombstoned car is flagged — not dropped, not resurrected.
- **S-7 — weakest point, an explicit protocol.** (1) The erasing device writes an `erasedAt` marker and **confirms relay ack before local reset**; the UI instructs destroying mnemonic artifacts. (2) The client reports the marker's timestamp T out-of-band; the purge deletes the owner's rows older than T, keeping the marker. (3) The wrapper's **owner denylist** blocks uploads under the erased OwnerId — else a months-late device pushing before pulling re-fills the relay (open issue #656). (4) A late device receives the marker and wipes; survivors re-onboard under a fresh mnemonic. Per-record purge doesn't exist (append-only history): inv. 30's "purge" = tombstone + relay ciphertext retention + **plaintext prior values in every device's SQLite** (a stolen unlocked phone reads "purged" data) — owner signs that tension.
- **S-8/S-9.** Next occurrence id = `createIdFromString(reminderId + anchor + rule + n)`, n counted from the anchor per the rule (tombstones included, never row counts) — double resolution collapses. Import: vehicle id = f(source id); record id = f(natural key + **ordinal among same-key rows**) — convergent across re-imports and devices, while legitimately identical rows (money-only fills, "common and kept") never silently collapse; same-key groups get a soft flag. Record-level dedup is the same mechanism.
- **S-11.** Writes hit local SQLite synchronously; sync is background catch-up; capture identical offline, online, dead-server.
- **S-12/S-13.** Synced prefs = `settings` singleton (deterministic id); device-local prefs stay in platform storage. Notifications schedule locally from synced state; phones alert, web never.
- **S-14.** 7.4.1 ships `SharedOwner` with per-mutation owner targeting — the model admits a second actor without rewrite. Honest sizing: re-upsert migration + blob-key re-wrapping; same-id-under-two-owners unverified; revocation = full re-key. Extension yes, "one-time job" no. Blob envelopes carry a key-id from day one.

## Blobs

Scans/PDFs never enter Evolu columns — bytes would live forever in append-only history on every device and burn relay quota. The client encrypts each file with a random per-file key (libsodium XChaCha20-Poly1305 on RN and web — **WebCrypto has no XChaCha20**), wrapped by a SLIP-21 subkey of the owner secret. The `document` row stores metadata + wrapped key + ciphertext hash (content-addressing by *ciphertext* hash; plaintext hashes leak equality); ciphertext goes to a ~200-line authenticated endpoint on the same VPS; clients lazy-download and cache. **Document deletion hard-deletes the ciphertext after a grace window** — the one place true server-side purge is possible — and GC bounds growth. A few hundred few-MB files → a few GB of disk. The largest bespoke component.

## Migration

`@koi/importer` (client-side, offline) maps every legacy id through `createIdFromString(legacyId)` and `upsert`s the one-JSON-document export in dependency order (cars/plans/planSwaps → readings/fills/entries/trips/policies/reminders → documents: encrypt, upload, upsert metadata), preserving `createdAt` (verified). Fresh install: local-only default → import legacy JSON via file picker, zero network → optionally "Turn on sync": generate mnemonic, show once + QR, background upload. Restore: enter/scan mnemonic → `restoreAppOwner` → full re-sync. Re-import or two-device import converges (S-9).

## Ops & cost

One VPS (Hetzner CX22-class): Docker compose = relay + denylist wrapper + SQLite volume, blob service, Caddy TLS. **€7–10/mo** — under D-009's €25; an estimate, no official relay sizing exists. Backup: the relay volume is ciphertext, safe to snapshot; the real backup is client-side JSON + document export — mnemonic loss makes server data unreadable by design. **Honest time budget:** 7.4.1 is a *frozen line* (last stable 2025-11-29; upstream all on v8-next; June-2026 bugs unanswered; sole committer) — bugfixes are self-serve fork patches; the bespoke inventory (blob service + GC, QR pairing, review queue + edit-stamps, erase protocol + wrapper, importer) re-buys most of the DIY time the E2EE brief credited Evolu with saving — ~2–3 months of 10 h/week runway. The strained budget is time, not money. Vendor death: MIT + pinned versions + self-hosted relay = nothing stops working; local data is plain SQLite; export doubles as the exit; sync swaps behind `KoiStore`, domain and UI untouched. Wire protocol v1 unchanged v7→v8; v8 is a library-API port, no migration guide, `restoreAppOwner`/`deleteDatabase` still missing on v8-next.

## Risks & spike candidates

Pre-registered kill criteria:
1. **RN/Expo reality** — Expo 54, two simulators, self-hosted relay; offline capture → merge → `refreshQueries`. Kill: capture-to-saved above platform norms; sync unreliable across restarts; op-sqlite flaky.
2. **Local-only floor** — proxy-audit a sync-unconfigured build. Kill: any un-disableable network call.
3. **Edit-stamp conflicts (S-5)** — concurrent same-column edits; derive the conflict set from `evolu_history` on a third, rebuilt device. Kill: missed concurrent pairs, false-positive floods, or crawling at 5k records.
4. **Erase runbook (S-7)** — marker-ack ordering, timestamp-bounded purge, denylist vs push-before-pull, months-late clock-skewed device. Kill: peers re-populate, or the marker can't survive purge ordering.
5. **Scale** — 5k records, initial sync on mid-range Android over mobile data. Kill: minutes-plural initial sync or pathological DB size.

Other: v8 churn; quarantine verified in source, not battle-tested; `ProtocolQuotaError` halts sync if quota misconfigured.

## Honest weaknesses

- S-5 surfacing is DIY (edit-stamps + history derivation) — RxDB's conflict handlers or CRDT-native engines do this out of the box.
- S-7 durable erase needs a bespoke protocol *and* a relay wrapper, on an engine that never physically deletes; server-readable candidates erase trivially.
- Append-only history contradicts inv. 30 and grows forever on every device — plaintext prior values included.
- No Swift SDK: irreversibly couples the stack to RN; if Evolu dies post-launch, the stack chosen for it remains.
- Blobs, pairing, review queue, erase, edit-stamps are all bespoke — Evolu covers less of Koi than "framework" suggests.
- Flat-mnemonic recovery forfeits the mandated KEK→DEK indirection; worst recovery UX on the shortlist.
- Frozen v7 line + bus factor 1 = fork-maintenance tail-risk from day one.

## Adversarial review (2026-07-17)

Method: S-1…S-14 walked against the design's mechanics; every suspicious engine-capability claim re-verified against primary sources (evolu.dev docs, GitHub source via API, npm registry). Verdict: **sound-with-fixes** — no fatal hole, but five majors that must amend the design before it competes at the gate.

**Engine claims verified (all hold):** `createIdFromString` deterministic SHA-256 → 21-char Id (docs API ref) · `evolu_message_quarantine` exists verbatim in `packages/common/src/local-first/Db.ts` — unknown table/column messages preserved, applied on schema update (`tryApplyQuarantinedMessages`), and propagated to peers via `union all` with `evolu_history` in `readDbChange`; partial split confirmed in source comment · `evolu_history` app-queryable with values+timestamps (time-travel doc, example query shown; "does not delete data — only marks it as deleted" verbatim) · `SharedOwner`/`SharedReadonlyOwner` + per-mutation `owner` (MutationOptions API ref; ShardOwner also exists) · issue #656 open, no relay owner-purge API, no maintainer response — and notably it *specifies* what durable erase needs (signed owner self-deletion, "Last Will"), confirming S-7 is DIY today · npm: `@evolu/common` 7.4.1 latest stable, `8.0.0-next.5` current prerelease; `@evolu/react-native` 14.3.0 — pins accurate.

### Major findings

**A1 · S-5/lineage (Plan.carIDs): the losing swap-append is dropped, and the promised detector cannot be deterministic.** Whole-column JSON LWW means concurrent appends converge to *one* device's lineage — the other appended car vanishes from converged state, exactly the "silent last-write-wins wearing a network" S-5 bans, on the record class Phase 2 called rare-and-momentous and demanded ordered-list merge behavior for. The design's only surfacing is the `evolu_history` forensics detector — but Evolu messages carry no causal metadata, only HLC timestamps, and concurrent-vs-sequential is **provably not derivable from the converged log** (a totally-ordered timestamp pair looks identical in both cases). Detection is possible only on a device that locally observes an overwrite of state the writer hadn't seen — so the "review queue derives identically on every device" property (true for odometer violations, which derive from converged data) does *not* extend to S-5 items; a third device, or any device rebuilt via `restoreAppOwner`, sees only the winner. Spike 3's kill criterion will likely fire as stated. Fix inside the architecture, should be the design, not the fallback: (a) lineage as append-only child rows (`planSwap`: planId, carId, swappedAt) — merge is union, nothing lost, order derived, anomalies flagged by the same derived review queue; (b) for scalar fields, either stamp edits with a base-version column (app-level causal metadata → concurrency deterministic from converged data) or conservatively surface every cross-device same-column overwrite within a window (false positives, no silent loss).

**A2 · S-7: the erase protocol loses two races and quietly forks the relay.** (a) *Marker identification:* the runbook says delete the owner's rows but leave the marker — yet the relay is blind; the operator cannot tell the marker from any other ciphertext row. Only timestamps are visible, so the erasing client must hand the marker timestamp out-of-band and the runbook becomes "delete owner rows with timestamp < T" — workable, nowhere written. (b) *Push-before-pull:* a months-offline device reconciling with the relay can upload its full local message set before applying the marker — the purged relay re-fills with the whole dataset's ciphertext under the old OwnerId. Erase is therefore not one-shot: it needs repeat purges forever, or a relay-side owner denylist — which is a fork/wrapper of the "official Docker image" the topology promises (it is precisely what open issue #656 asks upstream to build). (c) Crypto-erasure of re-uploads assumes the old mnemonic is destroyed — but the mnemonic is the user's own recovery artifact (paper, screenshot of the QR); erase must instruct its destruction. (d) Erase tapped while offline: the marker must be confirmed uploaded before local `resetAppOwner`, else survivors and late devices never learn. All fixable; Spike 4 must cover (a)–(d) explicitly, and the cost/ops story should own the denylist wrapper.

**A3 · S-9: natural-key deterministic ids silently merge distinct records.** `createIdFromString(vehicle+date+amount+odometer)` collapses two *legitimately different* records sharing the key — e.g. two money-only fills, same day, same amount, nil odometer, which §B3 says are "common and kept". Silent merge = silent data loss (S-5) inside the one path whose law is "imports never hard-fail; suspect rows are flagged". Fix: include the row's ordinal among same-key rows of the source file in the id input (stable across re-imports and across two devices importing the same CSV — convergence preserved), and flag same-key groups for review rather than collapsing.

**A4 · S-6: cascade atomicity rests on an unstated delivery assumption.** The parent-tombstone anchor covers a peer that has the parent tombstone but not all children — it does **not** cover the reverse arrival order. RBSR reconciliation may deliver a large batch across rounds; a peer applying child tombstones before the parent's renders a half-deleted car (car visible, records missing) — non-atomic as observed, an S-6 breach in a race. Cheap fix that also simplifies: cascade = **parent tombstone only** (single message, trivially atomic); children are already excluded by derivation per the design's own anchor, and individual child tombstones purge nothing anyway (append-only history). Undo = clear one flag.

**A5 · Solo-maintenance is undercounted; money is not.** Pinning 7.4.1 is not "budgeting a port when v8 lands" — it is adopting an *already-frozen* line today: last stable release 2025-11-29, all upstream effort on 8.0.0-next, June-2026 bug reports unanswered. Bugfixes are self-serve fork patches from day one. Add the bespoke inventory (blob channel + delete/GC, QR pairing, review queue, erase protocol + purge tooling + likely relay denylist wrapper, concurrent-edit mechanism per A1, invariant watcher) and the design re-buys most of the 30–60 h the E2EE brief credited Evolu with saving — at 10 h/week that is months of runway, and the doc lists the pieces but never sums them. Separately, the E2EE brief's verdict *mandated* KEK→DEK indirection + printed recovery code; the design forfeits it knowingly. That forfeit and the inv-30 tension are the same kind of thing: owner sign-off items, not weakness bullets. €7–10/mo infra survives scrutiny (blind relay + few GB blobs on one VPS); the strained budget is time, not money.

### Minor findings

- **WebCrypto has no XChaCha20-Poly1305** (AES-GCM/CBC/CTR only). The web blob path as written doesn't exist; use libsodium.js/wasm on web too, or AES-256-GCM everywhere.
- **Blob lifecycle absent:** no delete/GC on the blob endpoint — yet blobs are the only place true server-side per-record purge is *possible*. Document deletion should hard-delete ciphertext (heals inv. 30 for the heaviest, most sensitive class: scanned registration/insurance documents). Otherwise growth is unbounded.
- **Inv-30 sign-off understates local retention:** `evolu_history` keeps *plaintext* prior values and "deleted" records forever in every device's SQLite — a stolen unlocked phone reads purged data. The tension is not just relay-side ciphertext; the sign-off text must say so.
- **"Keep both" semantics undefined downstream:** a kept non-monotonic pair still feeds distance interpolation (inv. 21–23) → negative intervals. Domain must define it (e.g. the interval yields no number, mirroring `missedPrevious`) or the code will invent or fix — both banned.
- **S-13 unaddressed.** Compatible (per-device local scheduling from synced state; Evolu needs nothing), but the design should state it. Likewise the web companion's Safari-ITP key eviction (E2EE brief) — mnemonic re-entry after 7 idle days — is unmentioned.
- **Exit overclaim:** "swap sync behind KoiStore; UI untouched" holds only if KoiStore wraps *reads* (reactive queries) as well as mutations; the doc pins mutations only. State the read-side wrapper.
- **S-8 detail:** occurrence index n must be defined over the reminder's anchor+rule (counting tombstoned occurrences), never local row counts, or two devices diverge on n.
- **Household oversold as "one-time re-upsert job":** same-id rows under two owners is unverified semantics (collide or coexist?); old AppOwner copies need tombstoning; blob keys need re-wrapping to a shared key; a partner holding the SharedOwner secret means no member revocation without full re-key. S-14 non-preclusion genuinely holds — the sentence just promises more than verified.

### Verdict

**Sound-with-fixes.** No fatal: rung 1 stands (with the IP-visibility and flat-recovery caveats already declared), S-10/S-8 mechanics verified in source, the odometer walkthrough is mechanically real. But A1 (lineage/S-5 determinism) and A2 (erase races) must be redesigned as above before this design competes at the gate — as written they hand-wave two locked requirements behind spikes whose kill criteria are likely to fire; A3/A4 are cheap amendments; A5 reframes the adoption cost honestly. The fixes stay inside the Evolu architecture; none change the rung.

## Adversarial review — second pass (2026-07-17)

Method: the *revised* design attacked fresh — S-1…S-14 re-walked against the amended mechanisms, with special weight on the interactions *between* the first-pass fixes; suspicious engine claims re-verified against primary sources today. Verdict: **sound-with-fixes** — no fatal, four majors (two of them are first-pass fixes colliding with each other), seven minors.

**Engine claims verified this pass (2026-07-17):** protocol pairs **one HLC timestamp with one multi-column `DbChange`** — `EncryptedCrdtMessage { timestamp: Timestamp; change: EncryptedDbChange }`, change body encodes N `(column, value)` entries under that single timestamp (main-branch `Protocol.ts`; design asserts wire protocol v1 unchanged v7→v8) — this is what makes edit-stamp column attribution possible at all (see B1) · `evolu_history` rows are per-column `(table, id, column, value, timestamp)`, app-queryable, "Evolu does not delete data — it only marks it as deleted" (time-travel doc) · `@evolu/react-native` 14.3.0 peer-depends on `expo >=54`, `react-native >=0.81`, `@op-engineering/op-sqlite >=12`, `react-native-nitro-modules >=0.31`, `expo-sqlite >=16` (npm registry) — grounds B4 · note: `evolu.dev/docs/how-evolu-works` currently returns 404 (docs churn); claims re-anchored to source and the time-travel page.

### Major findings

**B1 · S-5 coverage hole: concurrent edit-vs-delete is detectable but not surfaced — the editor's input silently vanishes.** Delete is a mutation (sets `isDeleted`), so it carries `rev`/`baseRev` like any edit; an offline edit on B (touches `amount`) concurrent with a delete on A (touches `isDeleted`) shares a `baseRev` and is provably concurrent. But the design's surfacing rule is "**overlapping-column** pairs surface both values" — `amount` vs `isDeleted` don't overlap, so nothing is flagged. Converged state: a tombstoned record silently carrying B's fresh edit, excluded from every derivation on every device. That is user input discarded without surfacing — the exact S-5 sentence — in the most ordinary race this app will see (delete on the phone while editing on the web). The design flags a record *created* for a tombstoned parent but not a record *edited* while tombstoned elsewhere. Fix inside the mechanism, one derivation rule: any concurrent `baseRev`-sharing pair where either side touches `isDeleted` → review flag ("edited on one device, deleted on another — keep or discard?"). Spike 3 must include this case.

**B2 · Fix-collision: cascade = parent-tombstone-only (A4) starves the blob GC (first-pass minor), so car deletion never purges document ciphertext.** Blob hard-delete + GC is keyed to *document deletion*; under A4's cascade, child `document` rows are never individually tombstoned — only the car is. So the main deletion path (inv. 30: "Delete purges the car and everything attached", typed confirmation, the heaviest and most sensitive data class) leaves every scan's ciphertext on the VPS indefinitely, contradicting the design's own "the one place true server-side purge is possible." Fix: GC liveness must be computed from the **derived exclusion set** (a document is collectable when it is tombstoned *or* any ancestor car is), not from raw `document.isDeleted`. Cheap, but it must be stated — the two amendments as written cancel each other.

**B3 · S-7 residual races in the revised erase protocol.** (a) *Purge boundary points the wrong way:* "delete the owner's rows older than T" retains forever any messages other online devices push between marker-ack and denylist activation (timestamps > T, relay append-only) — the purge must be "everything except the marker's exact timestamp," run *after* the denylist engages, in that order. (b) *"Out-of-band" is a hand-wave with a product consequence:* S-7 plus the privacy page's "delete everything, any time" need a **self-serve authenticated wrapper endpoint** (proof of WriteKey / owner-secret possession); as written the channel is unspecified, so erase is either operator-toil-per-user (a support ticket inside a privacy promise) or an unauthenticated purge/denylist trigger (anyone who learns an OwnerId can sever a stranger's sync — availability attack). Auth protocol design belongs in the wrapper's bespoke inventory. (c) *Marker delivery through the denylist is assumed:* step 4 needs the denylist to be read-allow/write-deny **and** the client to apply downloaded messages even when its uploads are rejected mid-reconciliation; if a rejected write aborts the session client-side, the months-late device never receives the marker and never wipes — S-7's "every device" clause fails quietly. Spike 4's kill criteria must add (a) and (c) explicitly; (b) is a design amendment, not a spike.

**B4 · Vendor-death exit overclaims on the client edge; frozen-line maintenance is scheduled work, not tail-risk.** "MIT + pinned versions + self-hosted relay = nothing stops working" is true for the data, the relay, and the protocol — and false for the mobile build. `@evolu/react-native` 14.3.0 peer-pins a stack of fast-moving *native* dependencies (expo >=54, RN >=0.81, op-sqlite >=12, nitro-modules — npm, verified today), while Apple and Google mandate annual toolchain/target upgrades: the app must keep compiling against moving RN/Expo/OS floors with a frozen adapter whose upstream is entirely on v8-next. That converts fork maintenance from contingent bugfix risk into **recurring, non-declinable compatibility work on a cadence the platforms set** — on top of the 2–3-month bespoke sum, which excludes it. The Ops section should own an annual "frozen-line compatibility pass" line item (or make v8 adoption a scheduled milestone rather than an indefinite pin), and the exit paragraph should scope "nothing stops working" to server + data.

### Minor findings

- **B5 · Edit-stamp column attribution is real but unstated.** `rev`/`baseRev` alone don't say *which columns* an edit touched; the mechanism works only because one timestamp covers the whole multi-column DbChange (verified today), so history rows sharing the rev's timestamp are exactly that edit's columns. State this correlation, and the chain-walk rule (A edits thrice offline, B once: compare divergence-point leaves, not intermediates) — it is the load-bearing step Spike 3 exercises.
- **B6 · Blob-channel metadata undeclared.** PADMÉ covers relay messages; the bespoke blob endpoint still observes per-file ciphertext sizes, counts, and access timing (how many documents, roughly how big, when read). Pad/bucket blob sizes or extend the rung-1 caveat list — the privacy claim currently declares relay metadata only.
- **B7 · "Mnemonic never typed" overclaims for web pairing.** The zero-network path is browser-camera-scans-phone-QR; a camera-less desktop needs a typed-mnemonic fallback. Say so, or the pairing promise quietly excludes desktops.
- **B8 · S-9 ordinal ids assume stable source-file ordering.** If two export runs of the same MyCar data order same-key rows differently, the swapped ordinals cross-contaminate *non-key* fields (station, note) between the two ids under column LWW. Include the non-key fields in the id hash, or lean explicitly on the same-key soft flag as the catch.
- **B9 · planSwap completeness.** The lineage's *first* car must also be a `planSwap` row (or "last = current" breaks for never-swapped plans), and equal-`swappedAt` ties need a deterministic tie-break (id) before "order derives from swappedAt" is a total order.
- **B10 · Document undo can race blob GC.** Resurrection by id (S-6, any device, no stated horizon) after the grace-window hard-delete yields a metadata row with no bytes. Bound undo for documents to the grace window, or make resurrection re-upload from any device holding cache and *flag* (never fabricate) when the bytes are gone.
- **B11 · S-8 km-rule twins diverge in content.** Identity collapses (same id), but `dueMileageKm` computed from each device's local current-odometer differs between the twins; column LWW picks one silently. Benign (both the same user's intent, both plausible) but it contradicts the letter of "converge to the identical result" unless stated — or derive the km target from the merged trail at read time, S-3-style.
