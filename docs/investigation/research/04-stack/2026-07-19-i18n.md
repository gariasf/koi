# i18n for five locales across RN, web, and server — research brief

**Date:** 2026-07-19 · **Phase:** 4 (stack & platform fit) · **Author:** research subagent

**Verdict:** Use i18next everywhere — react-i18next on the RN and web clients, bare i18next core on the server — with one shared `@koi/i18n` JSON-catalog package and `i18next-cli` for extraction/lint/types; it is by far the most popular option (raised maturity weight, D-022) and the only one that is trivially the same library on all three targets.

## Findings

**Library health (all as of 2026-07-19, npm registry + GitHub API):** all three candidates are actively maintained — every one shipped a release in July 2026. Popularity is not close: i18next 18.6M weekly downloads and react-i18next 13.0M, vs react-intl 3.2M, vs @lingui/core 1.3M. i18next development is funded by locize (the maintainers' SaaS), but the library itself makes no network calls and locize is optional. Lingui is community-maintained. FormatJS shows healthy release cadence; it is historically a single-lead-maintainer project (longlho; not re-verified today, GitHub API rate limit).

**TS key-safety:** i18next is now the strongest of the three: ~~v26 (June 2026) enables the type-safe Selector API by default~~ **corrected (review):** the Selector API (`t($ => $.ns.key)`, v25.4+) is still opt-in via `enableSelector` in v26 — the docs' planned default flip never shipped; strict namespace mode landed in v26.1 — plus classic typed keys via `CustomTypeOptions` and `i18next-cli types` codegen (v26 changelog + docs, accessed 2026-07-19). Lingui avoids key drift by construction (source text is the message, macro-extracted) but offers no typed catalog keys. FormatJS relies on eslint-plugin-formatjs and extracted static ids — weakest compile-time story.

**ICU/plurals:** Lingui and FormatJS are ICU MessageFormat native. i18next uses JSON plural-suffix keys (`key_one`/`key_other`) resolved via `Intl.PluralRules`; full ICU is available via the `i18next-icu` plugin (371k/wk) but is unnecessary for Koi — stick to the default format that all i18next tooling assumes. Hermes still does **not** implement `Intl.PluralRules` (Hermes IntlAPIs doc, accessed 2026-07-19), so the RN app needs `@formatjs/intl-pluralrules` polyfill (634k/wk) regardless of library choice. `Intl.NumberFormat`/`DateTimeFormat` exist in Hermes (with option gaps) — number/date/currency rendering stays on raw `Intl` everywhere; message libraries carry text only (Hermes Intl details overlap with the domain brief).

**One catalog package across RN/web/server:** i18next is cleanest — catalogs are plain JSON, so `@koi/i18n` exports JSON resources plus a `createI18n()` factory; Metro, Vite/Next, and Node all import it with zero build step, and the server (a handful of email/export strings) uses i18next core with no React dependency. Lingui needs a compile step per target (metro-transformer on RN, plugin on web, precompiled catalogs for Node) and v6 went ESM-only (lingui.dev v6 announcement, accessed 2026-07-19) — friction if the NestJS server stays CJS. react-intl is React-only; server use means the separate `@formatjs/intl` API.

**Solo workflow, 5 locales:** `i18next-cli` v1.66.2 (i18next org, 410k/wk; replaced the unmaintained i18next-parser in Sept 2025 — repo README, accessed 2026-07-19) does extract, `lint` (hardcoded strings), `status` (per-locale health dashboard), `sync`, and type generation in one tool. Its auto-MT path is locize-tied; to avoid SaaS lock-in, machine-translate the plain JSON with an own-key/local LLM CLI (Intlayer CLI, self-hosted Languine, or a small script against any LLM API) — catalogs stay git-diffable JSON, no vendor holds them.

## Risks

- Hermes plural gap: forgetting the `intl-pluralrules` polyfill silently degrades plurals on device; pin it in the RN entrypoint and test a non-English plural in CI.
- i18next Selector API is 2025/2026-new — minor churn possible; classic `t('key')` remains supported as fallback.
- Catalog drift across 5 locales is process risk, not tooling risk; `i18next-cli status` in CI closes it cheaply.
- locize upsell is woven through i18next docs; harmless but keep MT scripted locally to preserve the no-SaaS stance.

## Koi fit

Privacy: pass — all candidates are offline, zero-telemetry libraries; MT stays local/own-key. Offline depth: catalogs bundle into every client. Solo maintainability: one library, one mental model, one CLI across three targets favors i18next decisively; Lingui would be a defensible second (nicest authoring ergonomics) but costs two extra build integrations and an ESM-only constraint. Maturity (raised, D-022): i18next is ~6× react-intl and ~14× Lingui by downloads — no justification exists for the niche picks. Cost: EUR 0. No refusal needed; this one is clear-cut.

## Adversarial review (2026-07-19)

**Verdict:** sound-with-fixes
**Corrections:**
- i18next v26 does **not** default-enable the Selector API — still opt-in via `enableSelector` (v26.0.0 changelog + docs, re-checked 2026-07-19); fixed in body. Docs tentatively plan to drop *type-level* string-key support in v27, so the `t('key')` fallback is safe now, not forever.
- All other versions/dates/stars verified exact; downloads within a week's drift (i18next 19.9M/wk today). Hermes `Intl.PluralRules` gap, Lingui v6 ESM-only (2026-04-22), and i18next-parser npm-deprecated in favor of i18next-cli (first publish 2025-09-25): all confirmed.

**Missed:**
- next-intl (4.5M/wk — now *larger* than react-intl): the dominant Next.js i18n library. Web-only, so the one-library verdict stands, but it deserved a named dismissal given the Next.js tiebreaker.
- Paraglide JS (inlang, ~453k/wk): rightly loses under D-022, but should be named.
- Locale *detection* uncovered: react-native-localize or expo-localization on RN, a language detector on web, to pick among the 5 locales.
